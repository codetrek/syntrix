# Field Naming Conventions

**Date:** December 30, 2025
**Status:** Canonical Reference
**Purpose:** Single source of truth for field names across all system components

## Overview

This document defines the canonical field names used throughout the Syntrix system. All components (storage, API, events, SDK) MUST use these exact names to ensure consistency.

**When in doubt, refer to this document.**

---

## 1. Identifier Fields

### 1.1 Database Identifier

| Context | Field Name | JSON Key | BSON Key | Notes |
| ------- | ---------- | -------- | -------- | ----- |
| Storage (Document) | `Database` | `database` | `database` | Stored in MongoDB |
| Storage (Event) | `Database` | `database` | - | Change stream events |
| Puller (`StoreChangeEvent`) | `Database` | `database` | - | Derived from `FullDocument.Database` when a document is available |
| API Response | - | `database` | - | Matches storage |

Puller derives the logical database from the available document image. A raw
physical delete can therefore have an empty `Database`; its `MgoDocID` still
contains the storage key. Store Watch independently validates the database
prefix in that key and returns the selected logical database in its events.

### 1.2 Document Identifier

| Context | Field Name | JSON Key | BSON Key | Notes |
| ------- | ---------- | -------- | -------- | ----- |
| Storage (Document) | `Id` | `id` | `_id` | Full path hash: `database:hash(fullpath)` |
| Storage (Event) | `Id` | `id` | - | References document ID |
| Puller (`StoreChangeEvent`) | `MgoDocID` | `mgoDocId` | - | Mongo document key, distinct from event identity |
| API Response | - | `id` | - | User-facing document ID |

**Rationale:**
- Storage uses short `id` / `_id` following MongoDB conventions
- Puller uses `mgoDocId` for source document identity and `eventId` for change identity

### 1.3 Event Identifier

| Context | Field Name | JSON Key | Notes |
| ------- | ---------- | -------- | ----- |
| Storage (Event) | `ChangeID` | `changeId` | Stable identity of one source change across watches and retries |
| Puller (`StoreChangeEvent`) | `EventID` | `eventId` | Puller event identity |

`Event.ChangeID` is issued by the Store and is separate from `Event.Id`, which
remains the document key. Neither field is an ordered checkpoint. Puller
currently creates its event identities through its direct Mongo ingestion path;
it does not consume Store `ChangeID` values.

`events.Transform` copies the Puller `EventID` into `SyntrixChangeEvent.Id`.
That business event's `Id` identifies the change; the available `Document.Id`
identifies the affected document, including when `Document` is a tombstone.

### 1.4. Store Watch Checkpoints

`WatchCheckpoint` is an opaque Store-issued string. It can be persisted or
transmitted, but callers must not inspect its backend encoding or compare its
bytes for ordering. `WatchStream.InitialCheckpoint()` establishes the initial
source boundary. Each `WatchFrame.Checkpoint` reports a completed source prefix,
including when `WatchFrame.Event` is nil. Persist it only after all required work
through that frame succeeds. Native resume tokens do not belong to
`storage.Event`. The [Watch contract](core/storage/03.stores.md#2-document-watch)
owns scope, source identity, and failure behavior.

### 1.5 JWT Claim Identifiers

| Context | Field Name | JSON Key | Notes |
| ------- | ---------- | -------- | ----- |
| JWT Claims | `Database` | `tid` | Legacy claim key retained |
| JWT Claims | `UserID` | `oid` | Legacy claim key retained |

**Rationale:** JWT claims keep `tid`/`oid` to preserve backward compatibility with existing tokens and integrations. The auth layer maps these to internal `Database`/`UserID` values.

## 2. Operation Types

### 2.1 Store Watch Event Types

Used in `storage.Event.Type`:

| Constant | Value | Description |
| -------- | ----- | ----------- |
| `EventCreate` | `"create"` | Document inserted, replaced, or restored from a tombstone |
| `EventUpdate` | `"update"` | Document modified |
| `EventDelete` | `"delete"` | Logical tombstone transition or physical removal; `Document == nil` for either |

These are source events from `DocumentStore.Watch`. Optional `Before` is a
requested source pre-image when available. The shared event does not expose the
Mongo operation type, so `EventDelete` alone does not distinguish business
deletion from physical cleanup.

### 2.2 Raw Puller Operation Types

Used in `StoreChangeEvent.OpType` (`opType` in JSON), as defined by
[Puller's event types](../../../internal/puller/events/types.go):

| Constant | Value | MongoDB Source | Description |
| -------- | ----- | -------------- | ----------- |
| `StoreOperationInsert` | `"insert"` | `insert` | Source document insertion |
| `StoreOperationUpdate` | `"update"` | `update` | Source update, including normal Syntrix deletion through a tombstone write |
| `StoreOperationReplace` | `"replace"` | `replace` | Source document replacement |
| `StoreOperationDelete` | `"delete"` | `delete` | Physical removal, including tombstone cleanup |

Puller currently reads Mongo directly and retains these operation types. Its
`StoreChangeEvent` name does not mean that it consumes Store Watch events.

### 2.3 Mongo Source Mapping to Store Watch

| MongoDB operationType | Storage EventType | Notes |
| --------------------- | ----------------- | ----- |
| `insert` | `create` or `delete` | Inserted state determines whether the document is live or a tombstone |
| `update` | `update`, `create`, or `delete` | Immutable `updateDescription.updatedFields.deleted` changes identify restoration or logical deletion |
| `replace` | `create` or `delete` | Replacement state determines whether the document is live or a tombstone |
| `delete` | `delete` | Physical removal; no `Document` payload |

### 2.4 Raw Puller Mapping to Business Events

[`events.Transform`](../../../internal/puller/events/transform.go) produces the
separate `SyntrixChangeEvent` consumed by the Trigger watcher:

| Raw Puller event | Business result |
|---|---|
| `insert` | `EventCreate` with the available document |
| `update` or `replace`, with `FullDocument.Deleted == true` | `EventDelete`, retaining the tombstone in `Document` |
| Other `update` | `EventUpdate` with the available document |
| Other `replace` | `EventCreate` with the available document |
| Physical `delete` | `ErrDeleteOPIgnored`; no business event |

A normal Syntrix `Delete` writes `deleted = true` and clears `data = {}` through
Mongo `UpdateOne`. Its business event belongs to that tombstone transition.
Later physical cleanup is garbage collection and must not create a second
business deletion. The current converter uses available lookup state, retains
the tombstone's metadata, and leaves `Before` unset; it does not guarantee a
historical deletion image. The
[document deletion lifecycle](core/storage/03.stores.md#document-deletion-and-physical-cleanup)
owns the full stored shape, rationale, and source/payload limits.

## 3. Timestamp Fields

### 3.1 Document Timestamps

| Field | Type | JSON Key | BSON Key | Description |
| ----- | ---- | -------- | -------- | ----------- |
| `CreatedAt` | `int64` | `createdAt` | `created_at` | Unix milliseconds, set once on creation |
| `UpdatedAt` | `int64` | `updatedAt` | `updated_at` | Unix milliseconds, updated on every write |

### 3.2 Event Timestamps

| Context | Field | Type | JSON Key | Description |
| ------- | ----- | ---- | -------- | ----------- |
| Storage Event | `Timestamp` | `int64` | `timestamp` | Unix nanoseconds; Mongo source cluster time has second precision |
| Puller Event | `Timestamp` | `int64` | `timestamp` | Unix milliseconds at normalization time |
| Puller Event | `ClusterTime` | `events.ClusterTime` | `clusterTime` | MongoDB source cluster time `{T, I}` |

Store event timestamps are metadata, not an ordering or resume position.
`WatchCheckpoint` carries the Store continuation; converting a Store timestamp
to a Puller representation requires an explicit unit and semantic decision.

**ClusterTime Format:**
```json
{
  "clusterTime": {
    "T": 1234567890,
    "I": 1
  }
}
```

- `T`: Seconds since Unix epoch
- `I`: Increment within the same second (ordinal, not time-based)

## 6. Document Content Fields

| Field | Type | JSON Key | BSON Key | Description |
| ----- | ---- | -------- | -------- | ----------- |
| `Data` | `map[string]interface{}` | `data` | `data` | User-defined content; cleared to `{}` in a tombstone |
| `Deleted` | `bool` | `deleted` | `deleted` | Tombstone flag; `true` means logically deleted |

Logical deletion retains identity, routing, version, and timestamp metadata.
`sys_expires_at` is a Mongo-only BSON date scheduling cleanup; it is not a field
of `StoredDoc` or its JSON payload. A tombstone's empty `data` cannot supply the
document's content before deletion.

## 7. Puller-Specific Fields

### 7.1 Current Puller Event Schema

The current [Go event types](../../../internal/puller/events/types.go) distinguish
the raw source change from its Puller progress envelope. These declarations use
`storage.StoredDoc` for document images and the local `ClusterTime` representation
described above:

```go
type PullerEvent struct {
    Change   *StoreChangeEvent `json:"change_event"`
    Progress string            `json:"progress"`
}

type StoreChangeEvent struct {
    EventID      string             `json:"eventId"`
    Database     string             `json:"database"`
    MgoColl      string             `json:"mgoColl"`
    MgoDocID     string             `json:"mgoDocId"`
    OpType       StoreOperationType `json:"opType"`
    FullDocument *storage.StoredDoc `json:"fullDoc,omitempty"`
    UpdateDesc   *UpdateDescription `json:"updateDesc,omitempty"`
    ClusterTime  ClusterTime        `json:"clusterTime"`
    TxnNumber    *int64             `json:"txnNumber,omitempty"`
    Timestamp    int64              `json:"timestamp"`
    Backend      string             `json:"backend,omitempty"`
}
```

`MgoColl` identifies the physical Mongo collection. Logical collection metadata
belongs to the available `FullDocument.Collection`. A raw physical delete may
have no `FullDocument`; an update or replacement without one is rejected by the
current normalizer. Prototype `NormalizedEvent` declarations are not the
implemented raw Puller schema.

### 7.2 UpdateDescription Schema

```go
type UpdateDescription struct {
    UpdatedFields   map[string]interface{} `json:"updatedFields,omitempty"`
    RemovedFields   []string               `json:"removedFields,omitempty"`
    TruncatedArrays []TruncatedArray       `json:"truncatedArrays,omitempty"`
}

type TruncatedArray struct {
    Field   string `json:"field"`
    NewSize int    `json:"newSize"`
}
```

## 9. Naming Convention Rules

### 9.1 Go Field Names

- Use `PascalCase` for exported fields
- Use `camelCase` for unexported fields
- Use the declared identity names: `Id` for a stored document and `MgoDocID` for a raw Puller source key

### 9.2 JSON Keys

- Use `camelCase` for all JSON keys
- Keep keys short but descriptive
- Exception: Puller's envelope uses `change_event`; its source change uses `opType`, `fullDoc`, and `updateDesc`
- Exception: JWT claims keep `tid` and `oid` for compatibility

### 9.3 BSON Keys

- Use `snake_case` for all BSON keys
- Exception: `_id` follows MongoDB convention
- Exception: `fullpath` - common developer idiom, kept as single word

### 9.4 Constants

- Use `PascalCase` for Go constants
- String values use `lowercase` (e.g., `EventCreate = "create"`)

## 11. Store and Puller Integration

Store events and Puller events are separate interfaces. Current Puller ingestion
uses a Mongo client directly, so these fields do not describe an implemented
Store-to-Puller adapter:

| Store value | Integration obligation |
|---|---|
| `Event.Id` | Preserve document identity independently of change identity |
| `Event.ChangeID` | Preserve stable source-change identity independently of Puller replay ordering |
| `Event.Database` | Preserve logical database scope |
| `Event.Type` | Define business conversion explicitly: Store `EventDelete` covers both logical deletion and physical cleanup |
| `Event.Document`, `Event.Before` | Preserve available payloads without claiming guaranteed historical images |
| `Event.Timestamp` | Preserve documented units and source-time meaning explicitly |
| `WatchFrame.Checkpoint` | Persist after required ingestion work, separately from the event payload |

The former Store API accepted raw `interface{}` resume tokens without a public
durable codec. Callers now use Store-issued `WatchCheckpoint` values. The Mongo
decoder does not infer legacy encodings; persisted old tokens require an explicit
migration or a deliberate new starting boundary. The
[Store Watch note](../../../.agents/notes/implemented/architecture/2026-09-08-store-watch-contract.md)
owns this change and the remaining Puller integration costs.
