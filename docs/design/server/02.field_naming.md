# Field Naming Conventions

**Status:** Canonical Reference

These names distinguish document state, source changes, business events, and
consumer progress. Each layer must preserve the meaning of an identifier when
mapping between representations.

## 1. Identifier Fields

### 1.1 Database Identifier

| Context | Field | JSON key | BSON key | Meaning |
|---|---|---|---|---|
| Stored document | `Database` | `database` | `database` | Logical database |
| Store event | `Database` | `database` | - | Selected watch database |
| Raw Puller event | `Database` | `database` | - | Logical database from the available document image |
| API response | - | `database` | - | Logical database |

Raw physical removal may have no document image and an empty Puller `Database`.
Its source document key retains database identity. Store Watch guarantees its
selected database scope independently of that optional image.

### 1.2 Document Identifier

| Context | Field | JSON key | BSON key | Meaning |
|---|---|---|---|---|
| Stored document | `Id` | `id` | `_id` | `database:hash(fullpath)` |
| Store event | `Id` | `id` | - | Affected document's storage key |
| Raw Puller event | `MgoDocID` | `mgoDocId` | - | Source document key |
| Business event document | `Document.Id` | - | - | Affected document, including a tombstone |
| API response | - | `id` | - | User-facing document ID |

### 1.3 Event Identifier

| Context | Field | JSON key | Meaning |
|---|---|---|---|
| Store event | `ChangeID` | `changeId` | One source change, stable across retries and watches of the same source |
| Raw Puller event | `EventID` | `eventId` | Puller source-change identity |
| Business event | `Id` | - | The corresponding Puller `EventID` |

Document identity, change identity, and checkpoint position are separate:

```text
same document key -> change A -> change B -> change C
                       |           |           |
                 checkpoint A checkpoint B checkpoint C
```

Neither a document key nor a change ID is an ordered checkpoint. Current Puller
identities are separate from Store `ChangeID`; Store/Puller ingestion integration
remains proposed work.

### 1.4. Store Watch Checkpoints

| Value | Contract |
|---|---|
| `WatchCheckpoint` | Opaque Store-issued string; persist/transmit without parsing, synthesis, or byte ordering |
| Initial checkpoint | Source boundary established before frames are read |
| Frame checkpoint | Completed source prefix, including a frame without an event |
| Consumer persistence | Only after required work through that frame succeeds |
| Native token | Backend-owned; absent from the shared Store event |

The [Watch contract](core/storage/03.stores.md#2-document-watch) owns source
identity, scope, progress, and failure behavior.

### 1.5 JWT Claim Identifiers

| Context | Field | JSON key | Meaning |
|---|---|---|---|
| JWT claims | `Database` | `tid` | Database claim |
| JWT claims | `UserID` | `oid` | User claim |

JWT retains `tid` and `oid` for compatibility with existing tokens and
integrations. The auth layer maps these claims to internal names.

## 2. Operation Types

### 2.1 Store Watch Event Types

| Constant | Value | Meaning |
|---|---|---|
| `EventCreate` | `create` | Live insertion, replacement, or restoration |
| `EventUpdate` | `update` | Document modification |
| `EventDelete` | `delete` | Logical tombstone transition or physical removal; nil `Document` |

These are source events. Optional `Before` is a requested source pre-image;
`EventDelete` alone cannot distinguish logical deletion from cleanup.

### 2.2 Raw Puller Operation Types

| Constant | `StoreChangeEvent.OpType` / JSON `opType` | Source meaning |
|---|---|---|
| `StoreOperationInsert` | `insert` | Document insertion |
| `StoreOperationUpdate` | `update` | Document update, including a normal tombstone deletion |
| `StoreOperationReplace` | `replace` | Document replacement |
| `StoreOperationDelete` | `delete` | Physical removal, including retention cleanup |

Raw Puller operations retain Mongo source meaning. The `StoreChangeEvent` type
belongs to Puller; it does not imply ingestion through Store Watch.

### 2.3 Mongo Source Mapping to Store Watch

| Source operation | Store event | Classification input |
|---|---|---|
| `insert` | `create` or `delete` | Live or tombstoned inserted state |
| `update` | `update`, `create`, or `delete` | Recorded change to the deletion flag, when present |
| `replace` | `create` or `delete` | Live or tombstoned replacement state |
| `delete` | `delete` | Physical removal |

### 2.4 Raw Puller Mapping to Business Events

| Source operation and available state | Business event | Document payload |
|---|---|---|
| `insert` | `create` | Available document |
| `update` or `replace` with `deleted=true` | `delete` | Tombstone with retained metadata and empty `data` |
| Other `update` | `update` | Available document |
| Other `replace` | `create` | Available document |
| Physical `delete` | None | None |

Business deletion belongs to the tombstone transition. Physical cleanup must
not create a second business deletion. Available state does not guarantee an
immutable image of every historical transition. The
[document deletion contract](core/storage/03.stores.md#document-deletion-and-physical-cleanup)
owns the lifecycle, responsibilities, and image limits.

## 3. Timestamp Fields

### 3.1 Document Timestamps

| Field | Type | JSON key | BSON key | Meaning |
|---|---|---|---|---|
| `CreatedAt` | `int64` | `createdAt` | `created_at` | Unix milliseconds at creation |
| `UpdatedAt` | `int64` | `updatedAt` | `updated_at` | Unix milliseconds at the latest write, including logical deletion |

### 3.2 Event Timestamps

| Context | Field | Type | JSON key | Meaning |
|---|---|---|---|---|
| Store event | `Timestamp` | `int64` | `timestamp` | Unix nanoseconds; Mongo source precision is seconds |
| Puller event | `Timestamp` | `int64` | `timestamp` | Unix milliseconds at normalization |
| Puller event | `ClusterTime` | `events.ClusterTime` | `clusterTime` | Source timestamp `{T, I}` |

| Cluster-time member | Meaning |
|---|---|
| `T` | Seconds since Unix epoch |
| `I` | Ordinal within the same second, not an elapsed duration |

A timestamp is not a Store continuation. Cross-layer mappings must preserve
units and source-time meaning explicitly.

## 4. Version Fields

| Field | Type | JSON key | BSON key | Meaning |
|---|---|---|---|---|
| `Version` | `int64` | `version` | `version` | Optimistic concurrency version; incremented on document modification or logical deletion |

## 5. Collection and Path Fields

| Field | Type | JSON key | BSON key | Meaning |
|---|---|---|---|---|
| `Collection` | `string` | `collection` | `collection` | Parent logical collection path |
| `CollectionHash` | `string` | `collectionHash` | `collection_hash` | Compact collection index hash |
| `Fullpath` | `string` | - | `fullpath` | Internal full document path |
| `Parent` | `string` | - | `parent` | Internal parent of the collection |

`Fullpath` and `Parent` are not exposed in document JSON responses. Raw Puller's
physical `MgoColl` is separate from the logical `Document.Collection`.

## 6. Document Content Fields

| Field | Type | JSON key | BSON key | Meaning |
|---|---|---|---|---|
| `Data` | Object | `data` | `data` | User content; `{}` in a tombstone |
| `Deleted` | `bool` | `deleted` | `deleted` | True for a logically deleted document |
| - | BSON date | - | `sys_expires_at` | Mongo-only tombstone cleanup deadline |

Tombstones retain identity, routing, version, and time metadata. Empty `data`
provides no deleted user content, and the cleanup deadline is not part of the
`StoredDoc` JSON payload.

## 7. Puller-Specific Fields

### 7.1 Current Puller Event Schema

```text
PullerEvent
  +-- change_event: StoreChangeEvent
  |     +-- source identity and provenance
  |     +-- operation and available document
  |     +-- source metadata
  +-- progress: Puller continuation
```

| Owner | Field | JSON key | Type or meaning |
|---|---|---|---|
| Envelope | `Change` | `change_event` | Raw `StoreChangeEvent` |
| Envelope | `Progress` | `progress` | String continuation |
| Change | `EventID` | `eventId` | Source-change identity |
| Change | `Database` | `database` | Logical database from available document state |
| Change | `MgoColl` | `mgoColl` | Physical Mongo collection |
| Change | `MgoDocID` | `mgoDocId` | Source document key |
| Change | `OpType` | `opType` | Raw source operation |
| Change | `FullDocument` | `fullDoc` | Optional `StoredDoc` image; required for update/replace processing |
| Change | `UpdateDesc` | `updateDesc` | Optional update delta |
| Change | `ClusterTime` | `clusterTime` | Source `{T, I}` timestamp |
| Change | `TxnNumber` | `txnNumber` | Optional transaction number |
| Change | `Timestamp` | `timestamp` | Normalization time in Unix milliseconds |
| Change | `Backend` | `backend` | Optional source backend name |

Physical removal may have no `fullDoc`. Current business conversion provides no
guaranteed historical after-image or `Before` payload. Payload capabilities and
source retention constrain how these fields can be used.

### 7.2 UpdateDescription Schema

| Field | JSON key | Type or meaning |
|---|---|---|
| `UpdatedFields` | `updatedFields` | Optional object of updated values |
| `RemovedFields` | `removedFields` | Optional list of removed field names |
| `TruncatedArrays` | `truncatedArrays` | Optional list of array truncations |
| Truncation `Field` | `field` | Array field name |
| Truncation `NewSize` | `newSize` | Resulting array length |

## 9. Naming Convention Rules

| Representation | Rule | Named exceptions |
|---|---|---|
| Go fields | Exported `PascalCase`; unexported `camelCase` | Preserve established identity names such as `Id` and `MgoDocID` |
| JSON | `camelCase`, short descriptive keys | Puller envelope `change_event`; JWT `tid` and `oid` |
| BSON | `snake_case` | Mongo `_id`; established `fullpath` |
| Constants | `PascalCase` identifiers; lowercase string values | For example, `EventCreate` represents `create` |

## 10. Field Mapping Quick Reference

| Concept | Document | Store event | Raw Puller event | Business event |
|---|---|---|---|---|
| Document identity | `Id` | `Id` | `MgoDocID` | Available `Document.Id` |
| Change identity | - | `ChangeID` | `EventID` | `Id` |
| Operation | - | `Type` | `OpType` | `Type` |
| Current/available state | The document | `Document` for create/update | `FullDocument` | `Document`, including tombstones |
| Previous state | - | Optional requested `Before` | No before-image field | No guaranteed `Before` |
| Continuation | - | Frame `Checkpoint` | Envelope `Progress` | `Progress` |

## 11. Store and Puller Integration

Current Store Watch and Puller ingestion are separate interfaces. Any future
adapter must preserve these obligations:

| Subject | Mapping obligation |
|---|---|
| Identity | Keep document identity, change identity, and replay position distinct |
| Scope | Preserve the logical database and collection membership guarantees |
| Deletion | Distinguish a business tombstone transition from physical cleanup |
| Images | Preserve available payloads without claiming historical retention |
| Time | Preserve units and source-time meaning |
| Progress | Persist only after required ingestion work; event receipt alone is insufficient |

Former untyped Store tokens require explicit migration or a deliberate new
starting boundary. The
[Store Watch note](../../../.agents/notes/implemented/architecture/2026-09-08-store-watch-contract.md)
owns the migration rationale, current implementation limits, and remaining
Puller integration costs.
