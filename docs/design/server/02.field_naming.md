# Field Naming Conventions

**Date:** December 30, 2025
**Status:** Canonical Reference
**Purpose:** Single source of truth for field names across all system components

## Overview

This document defines the canonical field names used throughout the Syntrix system. All components (storage, API, events, SDK) MUST use these exact names to ensure consistency.

**When in doubt, refer to this document.**

---

## 1. Identifier Fields

### 1.1 Database Identifier

| Context | Field Name | JSON Key | BSON Key | Notes |
| ------- | ---------- | -------- | -------- | ----- |
| Storage (Document) | `Database` | `database` | `database` | Stored in MongoDB |
| Storage (Event) | `Database` | `database` | - | Change stream events |
| Puller (StoreChangeEvent) | `Database` | `database` | - | **Shorter key for wire format** |
| API Response | - | `database` | - | Matches storage |

`database` consistently identifies the logical Syntrix database, including Puller payloads.

### 1.2 Document Identifier

| Context | Field Name | JSON Key | BSON Key | Notes |
| ------- | ---------- | -------- | -------- | ----- |
| Storage (Document) | `Id` | `id` | `_id` | Full path hash: `database:hash(fullpath)` |
| Storage (Event) | `Id` | `id` | - | References document ID |
| Puller (StoreChangeEvent) | `MgoDocID` | `mgoDocId` | - | Physical MongoDB document provenance |
| API Response | - | `id` | - | User-facing document ID |

**Rationale:**
- Storage uses short `id` / `_id` following MongoDB conventions
- Puller uses `mgoDocId` for the physical MongoDB identifier, distinct from `eventId`.

### 1.3 Event Identifier

| Context | Field Name | JSON Key | Notes |
| ------- | ---------- | -------- | ----- |
| Puller (StoreChangeEvent) | `EventID` | `eventId` | Unique per event, for deduplication |

`EventID` is assigned by the durable log as `v1-` plus SHA-256 of the
versioned, length-delimited configured source ID and complete BSON event resume
token. It identifies the event; opaque progress carries independent
source/generation/sequence positions. Cluster timestamps and hashes do not order replay.

### 1.4 JWT Claim Identifiers

| Context | Field Name | JSON Key | Notes |
| ------- | ---------- | -------- | ----- |
| JWT Claims | `Database` | `tid` | Legacy claim key retained |
| JWT Claims | `UserID` | `oid` | Legacy claim key retained |

**Rationale:** JWT claims keep `tid`/`oid` to preserve backward compatibility with existing tokens and integrations. The auth layer maps these to internal `Database`/`UserID` values.

## 2. Operation Types

### 2.1 Storage Event Types

Used in `storage.Event.Type`:

| Constant | Value | Description |
| -------- | ----- | ----------- |
| `EventCreate` | `"create"` | New document created |
| `EventUpdate` | `"update"` | Document modified |
| `EventDelete` | `"delete"` | Document deleted (soft delete) |

### 2.2 Puller Operation Types

Used in `StoreChangeEvent.OpType`:

| Constant | Value | MongoDB Source | Description |
| -------- | ----- | -------------- | ----------- |
| `OperationInsert` | `"insert"` | `insert` | New document |
| `OperationUpdate` | `"update"` | `update` | Field update |
| `OperationReplace` | `"replace"` | `replace` | Full document replace |
| `OperationDelete` | `"delete"` | `delete` | Document deleted |

**Mapping from MongoDB to Storage:**

| MongoDB operationType | Storage EventType | Notes |
| --------------------- | ----------------- | ----- |
| `insert` | `create` | Direct mapping |
| `update` | `update` | Direct mapping |
| `replace` | `update` | Treated as update |
| `delete` | `delete` | Direct mapping |

**Important:** Puller preserves MongoDB's original operation type (`insert`, `update`, `replace`, `delete`) for downstream consumers that need the distinction. Storage layer simplifies to three types.

## 3. Timestamp Fields

### 3.1 Document Timestamps

| Field | Type | JSON Key | BSON Key | Description |
| ----- | ---- | -------- | -------- | ----------- |
| `CreatedAt` | `int64` | `createdAt` | `created_at` | Unix milliseconds, set once on creation |
| `UpdatedAt` | `int64` | `updatedAt` | `updated_at` | Unix milliseconds, updated on every write |

### 3.2 Event Timestamps

| Context | Field | Type | JSON Key | Description |
| ------- | ----- | ---- | -------- | ----------- |
| Storage Event | `Timestamp` | `int64` | `timestamp` | Unix milliseconds |
| Puller Event | `Timestamp` | `int64` | `timestamp` | Unix milliseconds |
| Puller Event | `ClusterTime` | `events.ClusterTime` | `clusterTime` | MongoDB cluster time `{T, I}`; not replay position |

**ClusterTime Format:**
```json
{
  "clusterTime": {
    "T": 1234567890,
    "I": 1
  }
}
```

- `T`: Seconds since Unix epoch
- `I`: Increment within the same second (ordinal, not time-based)

## 7. Puller-Specific Fields

### 7.1 StoreChangeEvent schema

The canonical types are in `internal/puller/events/types.go`:

```go
type PullerEvent struct {
    Change   *StoreChangeEvent `json:"change_event"`
    Progress string            `json:"progress"`
}

type StoreChangeEvent struct {
    EventID      string             `json:"eventId"`
    Database     string             `json:"database"`
    MgoColl      string             `json:"mgoColl"`
    MgoDocID     string             `json:"mgoDocId"`
    OpType       StoreOperationType `json:"opType"`
    FullDocument *storage.StoredDoc `json:"fullDoc,omitempty"`
    UpdateDesc   *UpdateDescription `json:"updateDesc,omitempty"`
    ClusterTime  ClusterTime        `json:"clusterTime"`
    TxnNumber    *int64             `json:"txnNumber,omitempty"`
    Timestamp    int64              `json:"timestamp"`
    Backend      string             `json:"backend,omitempty"`
}
```

`change_event` can be nil for the initial position, progress-only delivery, or
heartbeat. Consumers preserve `progress` and save it after successful processing.
`backend` is a configured storage-backend name; the stable `source_id` belongs to
log metadata and the opaque progress contract. See
[Puller architecture](puller/01.architecture.md).

## 9. Naming Convention Rules

### 9.1 Go Field Names

- Use `PascalCase` for exported fields
- Use `camelCase` for unexported fields
- Suffix with type for clarity: `Database` not `Database`, `DocumentID` not `Document`

### 9.2 JSON Keys

- Use `camelCase` for all JSON keys
- Keep keys short but descriptive
- Exception: JWT claims keep `tid` and `oid` for compatibility

### 9.3 BSON Keys

- Use `snake_case` for all BSON keys
- Exception: `_id` follows MongoDB convention
- Exception: `fullpath` - common developer idiom, kept as single word

### 9.4 Constants

- Use `PascalCase` for Go constants
- String values use `lowercase` (e.g., `EventCreate = "create"`)

## 11. Event Transformation

MongoDB source changes are normalized into `StoreChangeEvent`, then the durable
Puller log assigns stable `EventID`. `events.Transform` produces the logical
`SyntrixChangeEvent` used by Streamer and Trigger. Soft-delete document state
controls logical delete/recreation semantics; physical MongoDB deletes represent
storage cleanup. Consumers must retain progress for deliberately ignored cleanup
events and fail on invalid transformations.

Payload field naming is separate from progress format. The versioned opaque
progress marker names source/generation/sequence positions and must not be
constructed from event timestamps or document IDs. Old timestamp/hash cursors
are rejected under the [Puller recovery contract](puller/01.architecture.md).
