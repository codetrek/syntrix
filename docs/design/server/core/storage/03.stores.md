# Storage Interfaces and Data Model

## 1. Store Interfaces

Application services use Store interfaces independently of the backend and its
routing topology. The [type definitions](../../../../../internal/core/storage/types/types.go)
own the Go API. Document operations take an explicit logical database; user
identity and token revocation remain global services.

### 1.1. DocumentStore

```go
type DocumentStore interface {
    Get(ctx context.Context, database string, path string) (*StoredDoc, error)
    GetMany(ctx context.Context, database string, paths []string) ([]*StoredDoc, error)
    Create(ctx context.Context, database string, doc StoredDoc) error
    Update(ctx context.Context, database string, path string, data map[string]interface{}, pred model.Filters) error
    Patch(ctx context.Context, database string, path string, data map[string]interface{}, pred model.Filters) error
    Delete(ctx context.Context, database string, path string, pred model.Filters) error
    DeleteByDatabase(ctx context.Context, database string, limit int) (int, error)
    Query(ctx context.Context, database string, q model.Query) ([]*StoredDoc, error)
    Watch(ctx context.Context, database string, collection string, after WatchCheckpoint, opts WatchOptions) (WatchStream, error)
    Close(ctx context.Context) error
}
```

`GetMany` preserves input order and returns a nil entry for a missing document.
`Delete` records a document tombstone. `DeleteByDatabase` physically removes
records from both data and system namespaces and returns the number removed;
a positive limit bounds the batch across both namespaces. The
[deletion lifecycle](#document-deletion-and-physical-cleanup) distinguishes these
operations and their change events.
The [multi-database design](05.multi-database.md) describes namespace selection
and isolation.

### 1.2. UserStore

```go
type UserStore interface {
    CreateUser(ctx context.Context, user *User) error
    GetUserByUsername(ctx context.Context, username string) (*User, error)
    GetUserByID(ctx context.Context, id string) (*User, error)
    ListUsers(ctx context.Context, limit int, offset int) ([]*User, error)
    UpdateUser(ctx context.Context, user *User) error
    UpdateUserLoginStats(ctx context.Context, id string, lastLogin time.Time, attempts int, lockoutUntil time.Time) error
    EnsureIndexes(ctx context.Context) error
    Close(ctx context.Context) error
}
```

User identities are global. The factory supplies the PostgreSQL implementation;
[User Store](06.user-store-postgres.md) owns its schema and behavior.

### 1.3. TokenRevocationStore

```go
type TokenRevocationStore interface {
    RevokeToken(ctx context.Context, jti string, expiresAt time.Time) error
    RevokeTokenImmediate(ctx context.Context, jti string, expiresAt time.Time) error
    RevokeTokenIfNotRevoked(ctx context.Context, jti string, expiresAt time.Time, gracePeriod time.Duration) error
    IsRevoked(ctx context.Context, jti string, gracePeriod time.Duration) (bool, error)
    EnsureIndexes(ctx context.Context) error
    Close(ctx context.Context) error
}
```

## 2. Document Watch

The [Watch types](../../../../../internal/core/storage/types/watch.go) expose an
ordered stream with explicit progress and terminal failures:

```go
type WatchCheckpoint string

type WatchOptions struct {
    IncludeBefore bool
}

type WatchFrame struct {
    Event      *Event
    Checkpoint WatchCheckpoint
}

type WatchStream interface {
    InitialCheckpoint() WatchCheckpoint
    Next(context.Context) (WatchFrame, error)
    Close() error
}
```

### 2.1. Scope and start boundary

`database` is required. An empty `collection` watches that database's ordinary
logical collections in the selected data namespace. A nonempty collection
selects exactly that logical collection, including nested paths. System
collections require an explicit selection such as `sys/rules`; an empty
collection does not include the system namespace. One call selects one source
through the [document router](04.routers.md), without discovering or aggregating
other databases or backends.

An empty `after` starts at a source-established current boundary. A successful
`Watch` returns a nonempty `InitialCheckpoint()` even when the source is idle.
This boundary excludes earlier changes; it does not enumerate existing documents
or establish a snapshot of them. Resuming returns the exact supplied checkpoint
as the initial checkpoint and yields changes after its completed prefix.

The Store owns checkpoint encoding. Callers may persist and transmit a
`WatchCheckpoint` as a string, but must not parse it, synthesize one, or compare
its bytes to determine order. A checkpoint is bound to the source incarnation,
logical database, collection selection, and options. Replacing a client, Store,
or Puller instance preserves resumability against the same retained source;
changing the source, scope, or `IncludeBefore` requires a deliberate new watch.
Invalid checkpoints and unavailable history return errors without resetting the
stream to the present.

### 2.2. Ordered processing and ownership

Each successful `Next` returns a nonempty checkpoint. `Event == nil` represents
ordered source progress without a document change, including progress past
excluded events or an idle batch. A progress frame may repeat the current
checkpoint. Save a frame's checkpoint only after its event, when present, and
all preceding required work have completed successfully. Receiving a frame does
not establish downstream durability or acknowledge a consumer's work.

`Event.Id` remains the affected document's storage key. `Event.ChangeID`
identifies the source change and is stable when that change is replayed or read
through another watch of the same source. Neither identity is an ordered
checkpoint. `Event.Timestamp` is Unix nanoseconds; the Mongo adapter uses source
cluster time with second precision. It is metadata, not a resume position.
Backend-native resume tokens belong to the Store implementation and do not
appear in the shared `Event` type.

Callers serialize `Next` calls. Returned frames remain valid after subsequent
reads. Canceling the context supplied to `Watch` or to a `Next` terminates the
subscription; later reads retain its terminal error. `Close` can interrupt a
blocked read and is idempotent. It owns only that subscription, leaving the
Store connection and other watches available. The Mongo implementation gives
native cursor cleanup a five-second timeout and returns cleanup failures.

### 2.3. Event payloads and Mongo prerequisites

`Document` is available document enrichment for create/update events; lookup may
observe state newer than the source change. `IncludeBefore` exposes a genuine
source pre-image when available. It does not guarantee retained historical
before/after payloads. The current
[Mongo Watch adapter](../../../../../internal/core/storage/mongo/watch.go)
emits `EventDelete` for both a logical tombstone transition and a physical
delete, with `Document == nil` in both cases. An ordinary-collections watch can
report a physical delete using its document identity alone. These source events
have different semantics from the business events produced by Puller's
`events.Transform`; the [deletion lifecycle](#document-deletion-and-physical-cleanup)
owns that distinction.

The Mongo implementation requires distinct physical data and system collection
names. If both settings select the same collection, `Watch` returns
`WatchUnsupported` before opening a cursor, because an ordinary-collections
watch could otherwise include system records. This prerequisite is enforced by
Watch; it does not change CRUD configuration handling.

The Mongo implementation keeps the existing `database:hash(fullpath)` document
keys. These identify the database on physical deletes but cannot recover the
logical collection path. For a specific collection, the implementation requests
available pre-images internally even when `IncludeBefore` is false, so it can
route using source metadata. If neither a pre-image nor document enrichment
provides the metadata needed to establish collection membership, the stream
fails with `WatchPayloadUnavailable`. Missing enrichment for a non-delete event
also fails explicitly. Unknown membership is never treated as another
collection or silently skipped.

Mongo pre-images are not enabled automatically. Operators must supply the source
capability and retained metadata needed for their selected scope; an optional
`Before` field is not a substitute for those routing prerequisites. Source
errors, malformed events, and cleanup errors remain visible to callers.

A Mongo watch reads the physical collection UUID and verifies that it remains
the same while opening the cursor. On a fresh watch, a missing selected physical
collection is created to establish that identity, including on an empty logical
database. Existing namespaces require metadata and change-stream read
permissions; creating one may additionally require collection-creation
permission. Permission failures are returned. Resuming a missing or replaced
collection fails with a source mismatch.

### 2.4. Failure categories and migration

`WatchError` carries a backend-independent code, logical database and collection,
and the original cause. `errors.As` exposes the category; `errors.Is` continues
to identify cancellation, deadlines, and other wrapped causes.

| Code constant | Meaning |
|---|---|
| `WatchInvalidScope` | Required watch scope is absent or invalid |
| `WatchInvalidCheckpoint` | The checkpoint encoding or continuation is invalid |
| `WatchScopeMismatch` | The checkpoint belongs to another logical scope or option set |
| `WatchSourceMismatch` | The source incarnation differs or has been invalidated |
| `WatchHistoryUnavailable` | The requested upstream history is unavailable |
| `WatchPayloadUnavailable` | Required event enrichment or scope metadata is unavailable |
| `WatchInvalidEvent` | The source event is malformed or cannot be represented |
| `WatchUnsupported` | Required watch capabilities or distinct physical data/system namespaces are unavailable |
| `WatchPermissionDenied` | Source authentication or authorization failed |
| `WatchSourceUnavailable` | The source or cursor failed for another reason |

The former channel API accepted an untyped raw token and had no public durable
codec. Callers migrate to the Store-issued `WatchCheckpoint` and explicit frame
processing. The Mongo decoder validates its versioned envelope strictly and
does not guess legacy encodings. Persisted raw tokens need an explicit migration
or deliberate new starting boundary; discarding an invalid token cannot claim
continuous recovery.

The [Store Watch decision](../../../../../.agents/notes/implemented/architecture/2026-09-08-store-watch-contract.md)
records source identity, alternatives, and the separate Puller integration work.

## 3. Internal Document Model

The default Mongo document representation is:

| Field | Stored meaning |
|---|---|
| `_id` | String `database:hash(fullpath)`, using the 128-bit path hash |
| `database` | Explicit logical database identifier |
| `fullpath` | Full document path |
| `collection` | Parent logical collection path |
| `collection_hash` | Compact hash used in database/collection indexes |
| `parent` | Parent of the collection |
| `data` | JSON document content; cleared to `{}` on document deletion |
| `version` | Optimistic concurrency version |
| `updated_at`, `created_at` | Unix millisecond document timestamps |
| `deleted` | Tombstone flag; `true` means the document is logically deleted |
| `sys_expires_at` | BSON date marking a tombstone's TTL cleanup deadline |

The Mongo Store directs ordinary paths to the configured data collection and
`sys` or `sys/...` paths to the configured system collection. Logical collection
paths share these physical namespaces.

## Document deletion and physical cleanup

### The stored lifecycle

A normal Syntrix document deletion is a state change. The
[Mongo `Delete` implementation](../../../../../internal/core/storage/mongo/document_store.go)
uses `UpdateOne` with the document key, logical database, caller preconditions,
and a predicate excluding existing tombstones. A successful write sets
`deleted = true`, clears `data` to `{}`, increments `version`, updates
`updated_at`, and sets `sys_expires_at` to the current time plus
`soft_delete_retention`. It preserves `_id`, `database`, `fullpath`, `collection`,
`collection_hash`, `parent`, and `created_at`.

For example, deleting `users/alice/posts/post-1` in database `accounts` turns a
live document with `version = 5` and `data = {"title": "Hello"}` into this stored
tombstone. Hash placeholders stand for the existing derived values;
`sys_expires_at` is shown as an Extended JSON BSON date:

```json
{
  "_id": "accounts:<128-bit path hash>",
  "database": "accounts",
  "fullpath": "users/alice/posts/post-1",
  "collection": "users/alice/posts",
  "collection_hash": "<collection hash>",
  "parent": "users/alice",
  "created_at": 1700000000000,
  "updated_at": 1700000001000,
  "version": 6,
  "deleted": true,
  "data": {},
  "sys_expires_at": {"$date": "2023-11-14T22:18:21Z"}
}
```

The example uses a five-minute retention interval. Retaining identity, routing,
version, and time metadata makes the logical deletion observable while clearing
the user content. `Get` and `GetMany` exclude tombstones; `Query` excludes them
unless `ShowDeleted` is set. `Delete` returns `ErrNotFound` for a missing or
already deleted document and `ErrPreconditionFailed` for an unmet precondition
on a live document.

```text
live document
    |
    | Syntrix Delete: Mongo UpdateOne (source operation "update")
    v
tombstone: deleted=true, data={}, retained identity and routing metadata
    |
    | later physical removal, normally TTL cleanup (source operation "delete")
    v
no stored record
```

TTL cleanup is garbage collection after the business deletion. It depends on
an applicable `sys_expires_at` TTL index and does not define another business
delete. The existing `EnsureIndexes` method defines that index for the ordinary
data collection; it does not install it on the separate system collection.
The expiry field alone does not guarantee physical cleanup. `DeleteByDatabase`
is a separate administrative purge: it uses `DeleteMany`, can remove live
records as well as tombstones, and does not perform per-document tombstone
transitions.

### Source operations and business events

The current [Puller ingestion loop](../../../../../internal/puller/core/puller.go)
opens Mongo change streams directly. Its
[normalizer](../../../../../internal/puller/normalizer/normalizer.go) retains the
source operation in `StoreChangeEvent.OpType`, including physical `delete`
operations. Despite its name, `StoreChangeEvent` is Puller's event type and does
not mean that Puller consumes `DocumentStore.Watch`.

The business conversion boundary is
[`events.Transform`](../../../../../internal/puller/events/transform.go):

| Puller source event | Business conversion |
|---|---|
| `update` or `replace` with an available `FullDocument.Deleted == true` | `SyntrixChangeEvent.Type = EventDelete`, retaining the tombstone in `Document` |
| Physical `delete` | Returns `ErrDeleteOPIgnored`; no business event is produced |

For a normal deletion whose lookup returns the tombstone, the event flow is:

```text
Mongo update -> raw Puller update + tombstone -> Transform -> business delete
Mongo delete -> raw Puller delete            -> Transform -> ErrDeleteOPIgnored
```

Consumers of raw Puller events must preserve this distinction when converting
to business events. Physical tombstone cleanup must not cause a second business
deletion. The current
[Trigger watcher](../../../../../internal/trigger/evaluator/watcher/watcher.go)
uses `events.Transform` at this boundary. A physical administrative purge also
returns `ErrDeleteOPIgnored` from this converter; it does not synthesize the
logical deletion transition that ordinary `Delete` would have written.

`DocumentStore.Watch` is a separate source API. Its Mongo adapter currently emits
`storage.EventDelete` for both the logical deletion and later physical removal,
with no `Document` payload for either event. `Before` is supplied only when
requested and available from the source. Two such frames represent two source
changes, not two business deletion requests. The shared Store event does not
carry the original Mongo operation type, so the raw Puller conversion table
cannot be applied to `Event.Type` alone. The [Watch contract](#2-document-watch)
retains its scope, source identity, payload, and failure requirements.

### Latest state and historical images

The tombstone is a retained latest-state record, not a copy of the deleted
content. Its empty `data` cannot supply the document's previous field values.
Historical before-images require separate source capability and retention;
keeping a tombstone does not provide them.

Puller requests Mongo [UpdateLookup](https://www.mongodb.com/docs/manual/changeStreams/#lookup-full-document-for-update-operations).
An update's `FullDocument` may reflect a
later state, including a recreation after deletion, and can be missing after
physical cleanup. The normalizer rejects update/replace events without
`FullDocument`; the current ingestion loop logs that error and skips that event.
`events.Transform` classifies update/replace events from the available document
state. This path therefore does not guarantee an immutable deletion after-image
or a business delete for every source tombstone update. Its `Before` field is
not populated by the current converter.

Store Watch also uses available lookup state for `Document`, but recognizes an
update's deletion transition from its immutable `updateDescription`. It still
requires enrichment for non-physical-delete source events, including tombstone
updates, and terminates with `WatchPayloadUnavailable` when that enrichment is
missing. Specific-collection watches additionally need routing metadata; a
physical delete without it also fails with `WatchPayloadUnavailable`. Optional
pre-images and retained source history do not make either path a historical
document journal or an end-to-end replay guarantee.

## 4. RoutedStore

`RoutedDocumentStore` implements the same interface and delegates to the selected
Store. Reads use `OpRead`, mutations use `OpWrite`, and watches use `OpWatch`.
The distinct watch operation keeps checkpoints tied to the authoritative write
source under read/write splitting. Database and operation routing errors
propagate to the caller. Closing the facade does not close shared providers;
the factory owns their lifecycle.
