# Storage Interfaces and Data Model

## 1. Store Interfaces

Stores separate application operations from backend placement and routing.
Document access is scoped to a logical database; identity and token revocation
are global services.

| Store | Responsibility | Scope |
|---|---|---|
| `DocumentStore` | Document state, queries, and source change streams | Explicit logical database |
| `UserStore` | User identity, profiles, and login state | Global |
| `TokenRevocationStore` | Revocation records and grace-period checks | Global |

### 1.1. DocumentStore

| Operation | Contract |
|---|---|
| `Get`, `GetMany` | Read live documents; `GetMany` preserves input order and uses nil entries for missing documents |
| `Create` | Establish a live document at its database-scoped path |
| `Update`, `Patch` | Replace or modify document content under caller preconditions |
| `Delete` | Record a logical deletion as a tombstone under caller preconditions |
| `DeleteByDatabase` | Physically purge data and system records; return the count, with a positive limit bounding the total batch |
| `Query` | Select documents in the requested logical collection; tombstones require `ShowDeleted` |
| `Watch` | Read ordered source changes and explicit checkpoints for one selected scope |
| `Close` | Release the Store's resources according to its ownership |

[Multi-database storage](05.multi-database.md) owns namespace selection and
isolation. [Document deletion](#document-deletion-and-physical-cleanup) owns the
distinction between a tombstone transition and physical removal.

### 1.2. UserStore

User operations cover creation, lookup by username or ID, listing, profile
updates, login state, index setup, and resource cleanup. The factory supplies
the PostgreSQL Store; [User Store](06.user-store-postgres.md) owns its schema and
behavior.

### 1.3. TokenRevocationStore

Revocation operations cover normal and immediate revocation, conditional
revocation with a grace period, revocation checks, index setup, and resource
cleanup.

## 2. Document Watch

A watch exposes source progress independently of event delivery:

```text
request: database + collection selection + after + IncludeBefore
                              |
                              v
                  selected authoritative source
                              |
                              v
initial checkpoint -> ordered {event?, checkpoint} frames -> terminal error
```

An absent event represents progress without a document change. A checkpoint
marks a completed source prefix; receiving it does not acknowledge downstream
work.

### 2.1. Scope and start boundary

| Selection | Meaning |
|---|---|
| Empty database | Invalid scope |
| Database + empty collection | That database's ordinary collections in the selected data namespace |
| Database + collection path | Exactly that logical collection, including a nested path |
| System collection, such as `sys/rules` | Requires explicit selection |
| One watch | One selected source; no database discovery or backend aggregation |

| Start | Contract |
|---|---|
| Empty `after` | Establish a nonempty current checkpoint, including on an idle source; exclude earlier changes |
| Saved `after` | Confirm that exact checkpoint and continue after its completed prefix |
| New current boundary | No existing-document enumeration or snapshot |
| Invalid continuation or missing history | Return an error; never silently restart at the present |

The Store owns checkpoint encoding. Callers may persist or transmit the opaque
string, but must not parse it, synthesize one, or compare its bytes for ordering.

A checkpoint binds the physical source incarnation, logical database, collection
selection, and options. Replacing a client or service preserves the binding to
the same retained source. Changing the source, scope, or `IncludeBefore`
requires a deliberate new watch.

### 2.2. Ordered processing and ownership

```text
read frame N -> finish all required work through N -> persist checkpoint N
read frame N+1 -> ...
```

| Owner or value | Obligation |
|---|---|
| Store | Every successful frame has a nonempty checkpoint; progress-only frames may repeat it |
| Caller | Serialize reads and save progress only after all preceding required work succeeds |
| Returned frame | Remains valid after subsequent reads |
| `Event.Id` | Identifies the affected document's storage key |
| `Event.ChangeID` | Identifies one source change stably across retries and watches of the same source |
| `Event.Timestamp` | Unix nanoseconds at source precision; Mongo provides second precision; neither identity nor timestamp is a checkpoint |
| Backend adapter | Own native continuation tokens; keep them out of the shared event |
| Cancellation | Canceling the watch or a read terminates the subscription; later reads retain the terminal error |
| Subscription close | Idempotently interrupt blocked reads, bound cleanup, and report cleanup failures |
| Shared resources | Closing a subscription leaves the Store connection and other watches available |

### 2.3. Event payloads and Mongo prerequisites

| Payload | Availability and limit |
|---|---|
| Create/update `Document` | Available enrichment is required; it may reflect state newer than the source change |
| Delete `Document` | Nil for both logical deletion and physical removal |
| `Before` | A genuine source pre-image, exposed only when requested and available |
| Tombstone update | Still requires enrichment even though its emitted delete event has no `Document` |
| Physical delete across ordinary collections | Document identity alone can establish database membership |
| Specific-collection event | Requires image metadata establishing logical collection membership |
| Missing required payload or membership | Terminal `WatchPayloadUnavailable`; never emit an unknown scope or silently skip it |

The key `database:hash(fullpath)` preserves database identity after removal, but
its hash cannot reveal the collection path. A specific-collection watch may
therefore need source pre-images for routing even when `IncludeBefore` is false.

| Mongo prerequisite | Reason and failure behavior |
|---|---|
| Distinct physical data and system collections | Prevent system records entering ordinary-collection watches; an identical mapping returns `WatchUnsupported` |
| Stable physical collection identity | Detect replacement or invalidation; resume against a missing or replaced source fails |
| Metadata and change-stream permission | Required to establish the source and read its history; permission failures propagate |
| Collection-creation permission when needed | A fresh watch may create a missing selected namespace to establish an idle starting boundary |
| Appropriate source retention and image capability | Supply history and scope metadata; pre-images are not enabled automatically |

These are Watch prerequisites; they do not redefine CRUD configuration handling.
Optional images provide no retained historical before/after guarantee. The
[deletion lifecycle](#document-deletion-and-physical-cleanup) distinguishes these
source payloads from business deletion events.

### 2.4. Failure categories and migration

`WatchError` carries the selected scope, a backend-independent category, and the
original cause. Callers can inspect the category while retaining cancellation,
deadline, and backend error identity. Malformed events, decode failures, and
source cursor failures terminate the stream.

| Category | Meaning |
|---|---|
| `WatchInvalidScope` | Required watch scope is absent or invalid |
| `WatchInvalidCheckpoint` | Checkpoint encoding or continuation is invalid |
| `WatchScopeMismatch` | Checkpoint belongs to another logical scope or option set |
| `WatchSourceMismatch` | Source incarnation differs or has been invalidated |
| `WatchHistoryUnavailable` | Requested upstream history is unavailable |
| `WatchPayloadUnavailable` | Required enrichment or scope metadata is unavailable |
| `WatchInvalidEvent` | Source event is malformed or cannot be represented |
| `WatchUnsupported` | Required capabilities or distinct physical namespaces are unavailable |
| `WatchPermissionDenied` | Source authentication or authorization failed |
| `WatchSourceUnavailable` | Source or cursor failed for another reason |

Persisted tokens from the former untyped API require an explicit migration or a
deliberate new starting boundary. Store checkpoints use strict validation without
legacy inference; discarding a token cannot claim continuous recovery. The
[Store Watch decision](../../../../../.agents/notes/implemented/architecture/2026-09-08-store-watch-contract.md)
owns the rationale, implementation evidence, and remaining integration costs.

## 3. Internal Document Model

| Stored field | Meaning |
|---|---|
| `_id` | `database:hash(fullpath)`, with a 128-bit path hash |
| `database` | Logical database identifier |
| `fullpath` | Full document path |
| `collection`, `collection_hash` | Logical collection path and its compact index hash |
| `parent` | Parent of the collection |
| `data` | User document content |
| `version` | Optimistic concurrency version |
| `created_at`, `updated_at` | Unix millisecond document timestamps |
| `deleted` | Tombstone flag; `true` means logically deleted |
| `sys_expires_at` | BSON date for a tombstone's cleanup deadline |

Ordinary paths share the data namespace; `sys` and `sys/...` paths use the system
namespace. [Field naming](../../02.field_naming.md) owns the JSON/BSON mappings.

## Document deletion and physical cleanup

### State transitions

Logical deletion must remain observable after user content is removed. A
retained tombstone supplies document identity, routing metadata, version, and
deletion time until physical cleanup.

```text
live document
    |
    | document Delete: logical state change; source operation "update"
    v
tombstone: deleted=true, data={}, retained identity and routing metadata
    |
    | retention cleanup: physical source operation "delete"
    v
no stored record
```

| Stored value | Live example | After logical deletion |
|---|---|---|
| `_id` | `accounts:<path hash>` | Unchanged |
| `database` | `accounts` | Unchanged |
| `fullpath` | `users/alice/posts/post-1` | Unchanged |
| `collection`, `collection_hash`, `parent` | `users/alice/posts`, its hash, `users/alice` | Unchanged |
| `created_at` | Creation time | Unchanged |
| `data` | `{"title": "Hello"}` | `{}` |
| `deleted` | False | True |
| `version` | 5 | 6 |
| `updated_at` | Previous write time | Deletion time |
| `sys_expires_at` | Absent | Deletion time plus `soft_delete_retention` |

| Operation | State and visibility contract |
|---|---|
| Document `Delete` | Apply caller preconditions to a live document and write the tombstone |
| Repeated delete or absent document | `ErrNotFound`; no new tombstone transition |
| Unmet precondition on a live document | `ErrPreconditionFailed` |
| Ordinary reads | Exclude tombstones; `Query` requires `ShowDeleted` to include them |
| Retention cleanup | Remove the tombstone when cleanup is available; require an applicable TTL index, not only an expiry field |
| Database purge | Physically remove data and system records, including live records; no per-document tombstone transition |

Physical cleanup is garbage collection. It must not generate a second business
deletion. Database purge is an administrative operation with a separate lifecycle.

### Event responsibilities

Source changes and business transitions have different consumers and payloads:

```text
                        +-> raw Puller events -> business conversion -> consumers
Mongo source changes ---+
                        +-> Store Watch source frames
```

The paths are separate today. Puller ingestion through Store Watch remains
proposed work.

| Layer | Logical tombstone transition | Physical removal |
|---|---|---|
| Mongo source | `update` for normal document deletion | `delete` |
| Raw Puller event | Preserve the source operation and available document | Preserve the physical operation, which may have no document image |
| Business event conversion | An available tombstone on `update`/`replace` produces business `delete`, retaining the tombstone metadata | No business event |
| Store Watch | `EventDelete`, with nil `Document` | `EventDelete`, with nil `Document` |

- Business conversion owns deletion semantics; raw source operation names are
  insufficient without the document state.
- Store Watch's optional `Before` is a requested source pre-image. Its shared
  event type does not expose the original Mongo operation, so `EventDelete`
  alone cannot distinguish logical deletion from cleanup.
- Two Store delete frames can represent two source changes for one business
  deletion. A physical database purge does not synthesize missing tombstones.

### Retention and historical-image limits

| Available information | Supports | Does not establish |
|---|---|---|
| Tombstone metadata | Latest deleted state, identity, routing, version, and time | Deleted user content; `data` is empty |
| Current document enrichment | Processing with available state | An immutable image of every past transition; state may be newer or absent |
| Optional source pre-image | Prior state when capability and retention permit | Guaranteed historical images or automatic image retention |
| Store checkpoint | Continuation within retained source history | A document snapshot, consumer durability, or end-to-end replay |
| Cleanup deadline | Retention policy in a namespace with configured cleanup | Automatic cleanup in every physical namespace |

Current Puller business payloads provide no guaranteed `Before` image or
preservation of every historical logical transition. Missing required Store
payloads remain terminal failures under the [Watch contract](#2-document-watch).
Implementation gaps and evidence belong to the
[Store Watch decision](../../../../../.agents/notes/implemented/architecture/2026-09-08-store-watch-contract.md).

## 4. RoutedStore

| Concern | Responsibility |
|---|---|
| Database placement | Select the configured backend topology |
| Reads | Route with `OpRead` |
| Mutations | Route with `OpWrite` |
| Watches | Route with `OpWatch` to preserve the authoritative source binding |
| Routing errors | Propagate to the caller |
| Facade close | Leave shared providers open; the factory owns their lifecycle |

Under read/write splitting, receiving a primary-source event does not make
replica reads current. [Document routing](04.routers.md) owns topology selection.
