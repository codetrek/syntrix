# Multi-Database Storage

## 1. Goals and Implemented Scope

Logical databases share infrastructure by default. Dedicated backends isolate
selected databases' load and failures while preserving the same document API.

| Concern | Contract |
|---|---|
| Document operations | Always carry an explicit logical database |
| HTTP document APIs | Carry that database in the [URL](../../gateway/06.api-url-structure.md) |
| Isolation | Database-aware keys and predicates separate records in shared namespaces |
| User identity and revocation | Remain global services |
| Store operations | Follow the [Store contracts](03.stores.md) regardless of placement |

## 2. Document Identity and Physical Namespaces

```text
logical database + document path
               |
               v
    database:hash(fullpath) -----> database identity survives physical removal
               |
               v
  ordinary path -> data namespace
  sys or sys/... -> system namespace
```

| Stored information | Responsibility |
|---|---|
| `database` | Explicit logical database identity |
| `_id = database:hash(fullpath)` | Distinguish equal paths across databases; use a 128-bit path hash |
| `collection`, `collection_hash`, `fullpath` | Supply logical collection membership; the document-key hash cannot recover it |
| Physical Mongo database | Backend namespace, independent of the logical database field |
| Data/system collections | Each may hold records for multiple logical databases |

| Lifecycle action | Database-scoped effect |
|---|---|
| Document deletion | Retain a tombstone's identity and metadata; clear user content |
| Ordinary reads | Exclude tombstones |
| Physical retention cleanup | Garbage-collect tombstones; no second business deletion |
| Database purge | Remove data and system records, including live records, without per-document tombstones |

The [document deletion contract](03.stores.md#document-deletion-and-physical-cleanup)
owns the state transitions and payload rules. Cleanup requires an applicable TTL
index in each selected physical namespace; an expiry field alone provides no
cleanup guarantee. Watches retain the document-key scheme and add no independent
change journal to writes.

## 3. Database and Operation Routing

```text
logical database
      |
      +-> explicit dedicated binding -> one Store for all operations
      |
      +-> default document topology
                    |
                    +-> OpRead ---------> replica
                    +-> OpWrite/OpWatch -> primary
                         (read_write_split)
```

| Configuration or change | Meaning |
|---|---|
| `storage.topology.document` | Select the default document topology |
| Explicit non-default `storage.databases` entry | Bind that database to its named backend |
| Unlisted logical database | Use the default topology and retain database-scoped predicates |
| Required `default` entry | Must reference a valid backend; does not override the topology's primary/replica selection |
| Dedicated binding | Currently one Store for reads, writes, and watches |
| Changed binding | Does not copy documents, transfer retained history, or migrate checkpoints |

Watch routing uses the authoritative write source. Ordinary replica reads need
not be current with a received event. Dedicated primary/replica routing remains
a [proposed extension](../../../../../.agents/notes/proposed/architecture/2026-09-07-dedicated-backend-read-write-routing.md).

## 4. Watch Isolation and Recovery

Example selection: `database=accounts`, `collection=orders`, and a saved opaque
checkpoint select that logical collection through its configured Store.

| Boundary | Obligation |
|---|---|
| Database | Required; every emitted event belongs to it |
| Empty collection | Ordinary collections in the selected data namespace |
| System collection | Explicit selection, such as `sys/rules` |
| Physical namespaces | Mongo Watch requires distinct data/system names; otherwise `WatchUnsupported` |
| One watch | One selected source; no database discovery or backend aggregation |
| Checkpoint | Bind the source incarnation, database, collection selection, and options |
| Changed or unavailable history | Return an explicit error; never silently restart at the present |

| Event scope | Required information |
|---|---|
| Physical delete across ordinary collections | Database identity from the document key is sufficient |
| Specific logical collection | Available image metadata must establish membership |
| Source operation other than physical delete | Required document enrichment must be available |
| Missing required membership or payload | Terminal `WatchPayloadUnavailable`; neither emit unknown scope nor silently skip it |

Store Watch reports both logical deletion and physical removal as `EventDelete`,
with nil `Document` and optional requested `Before`. These source frames do not
define additional business deletions.

- Replacing a client or Store preserves continuation against the same retained
  source; replacing the physical collection does not.
- A fresh watch may create a missing physical namespace to establish an idle
  starting boundary. Metadata, change-stream, and applicable creation
  permissions are prerequisites.
- Routing may require pre-images even when `IncludeBefore` is false. Image
  capability and retention are operational prerequisites, not automatic setup.

The [Watch contract](03.stores.md#2-document-watch) owns frame ordering,
cancellation, payloads, and errors. The
[Store Watch decision](../../../../../.agents/notes/implemented/architecture/2026-09-08-store-watch-contract.md)
owns source-identity rationale and implementation evidence.

## 5. Configuration Example

A shared split topology and a dedicated document binding:

```yaml
storage:
  databases:
    default:
      backend: shared_mongo
    accounts:
      backend: accounts_mongo
  backends:
    shared_mongo:
      type: mongo
      mongo:
        uri: mongodb://shared-primary:27017
        database_name: shared_data
    shared_replica:
      type: mongo
      mongo:
        uri: mongodb://shared-replica:27017
        database_name: shared_data
    accounts_mongo:
      type: mongo
      mongo:
        uri: mongodb://accounts-primary:27017
        database_name: account_data
  topology:
    document:
      strategy: read_write_split
      primary: shared_mongo
      replica: shared_replica
      data_collection: documents
      sys_collection: sys
      soft_delete_retention: 5m
```

| Logical database | Watch/write source | Ordinary read source |
|---|---|---|
| `accounts` | `accounts_mongo` | `accounts_mongo` |
| Other databases | `shared_mongo` | `shared_replica` |

Global user and revocation settings are outside this document-topology excerpt.

## 6. Migration and Integration Boundaries

| Boundary | Required distinction |
|---|---|
| Document keys | Preserve existing database-aware identities |
| Former untyped resume tokens | Require explicit migration or a deliberate new boundary that accounts for omitted history |
| Store checkpoints | Strict source/scope binding; no runtime legacy-token inference |
| Current Puller ingestion | Separate direct Mongo source; Store Watch does not supply its buffer, checkpoints, or recovery |
| Raw source and business events | Preserve physical operations at the source layer; suppress physical cleanup as a business deletion |
| Future Store/Puller integration | Must establish its own durable progress, aggregation, and consumer recovery contracts |

Store validation alone provides no end-to-end Puller durability or recovery
guarantee. The [Store Watch note](../../../../../.agents/notes/implemented/architecture/2026-09-08-store-watch-contract.md#consequences)
records the separate integration decisions and their costs.
