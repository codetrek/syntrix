# Indexer Service Architecture

Status: active design with implemented ingestion and separate recovery work

Indexer maintains secondary indexes derived from authoritative document storage.
Separating maintenance from Query lets index storage and rebuild policy evolve
without changing document CRUD. Current stores are memory and Pebble; store
selection is isolated behind the existing index-store contract.

## Current components

```text
MongoDB -> Puller durable log -> shared local/gRPC Subscription.Next()
                                          |
                                          v
                                 transform and apply
                                          |
                                          v
                              Manager -> memory / Pebble index
                                          |
                                          v
                               save processed progress

Query -> Indexer.Search -> template selection -> bounded index lookup
  |
  +-> fetch returned document references from Storage
```

`service.go` loads templates and stored progress, then consumes Puller
sequentially. `manager/` owns template matching and index routing. `encoding/`
owns ordering keys; `template/` owns template parsing; `mem_store/` and
`persist_store/` implement the stores. `grpc/` and `client/` adapt the public
search/health/stats APIs. `rebuild/` and `reconciler/` contain recovery components
whose production lifecycle is still incomplete.

## Puller ingestion and progress

The service calls `Subscribe(ctx, SubscribeOptions{ConsumerID, After})` and owns
the resulting `Subscription.Next(ctx)` / `Close()` lifetime. The first envelope
is progress-only. Subsequent progress-only envelopes also complete a prefix
without requiring a document update.

Progress is the complete opaque source/generation/sequence marker, not an event
ID or MongoDB token. The service applies an event successfully before saving its
progress. Transformation, application, checkpoint, and terminal upstream errors
stop consumption and remain visible through health/lifecycle results. The
persistent store retains asynchronous batch failure and rejects later
checkpoint saves, so failed index writes cannot be acknowledged by later events.

Live events arrive from Puller's committed memory batch. Saved progress replays
retained history through the same local and gRPC state machine. Invalid format,
source/generation mismatch, and expired history fail explicitly; they do not
silently start at the current head. See the
[Puller contract](../puller/02.adaptive-consumption.md).

The store owns saved progress. A persisted marker alone does not reconstruct a
lost memory index, and retained replay cannot recover documents older than the
log. Full startup/rebuild integration remains in
[Indexer recovery](../../../../.agents/notes/proposed/architecture/2026-09-07-indexer-recovery-lifecycle.md).

## Search and index representation

Indexer selects a matching template using the collection, filters, and ordering
in a query plan. Query receives document references and fetches authoritative
documents from Storage. Template selection remains inside Indexer; callers do
not depend on template implementation details.

Indexes are isolated by logical database and template/collection identity.
Ordering keys encode field values and direction, with document ID as a tie-breaker.
The query cursor uses that ordering-key encoding; it is distinct from Puller's
source progress marker. See [index details](02.index.md) for template conflict
rules, matching, ordering-key encoding, and in-memory representation.

[Query integration](../query/02.indexer-integration.md) owns missing/rebuilding
index behavior. Incomplete indexes must return explicit unavailability; this
architecture does not promise an automatic storage-scan fallback or a ready
index before reconstruction finishes.

## Recovery design still to integrate

The recovery owner must connect reconciliation, storage scanning, replay, job
fencing, and shutdown. The intended sequence is:

```text
Capture durable replay start
            |
            v
Mark affected index rebuilding
            |
            v
Scan authoritative documents with stable pagination
            |
            v
Apply retained events through a fixed replay cut
            |
            v
Join live processing without a gap
            |
            v
Commit index state and checkpoint before marking healthy
```

Jobs need bounded batches, concurrent-job limits, cancellation, and template
replacement fencing. A gap invalidates the rebuild; current data cannot be
certified complete by simply clearing a checkpoint. Memory-store restart requires
reconstruction, while intact persistent data can resume only from a verified
checkpoint. The future management APIs are described in
[management RPCs](../../../../.agents/notes/proposed/feature/2026-09-07-indexer-management-rpcs.md).

An Indexer-owned event spool was considered for long and concurrent rebuilds:
writing once could serve many replay readers, use a rebuild-specific retention
period, and isolate cleanup from Puller's default one-hour history. This remains
a proposed integration choice, not a current local event buffer. Direct reuse
of `internal/puller/buffer` is not an established contract: its source-token and
mutation ownership belongs to Puller. A future spool must preserve the original
source/generation/sequence and event identity, with bounded storage and an
explicit history-loss result. Timestamp/hash sorting cannot substitute for that
position.

A memory-only WAL was considered insufficient for large rebuilds because bounded
capacity can be exhausted while the authoritative scan continues. Retaining a
separate disk spool adds storage, lifecycle, cleanup, and ownership costs; the
recovery implementation must decide those costs against extending source-log
retention before exposing indexes as healthy.

## Configuration

```yaml
indexer:
  puller_addr: localhost:9000
  template_path: index_templates
  progress_path: indexer/progress
  consumer_id: indexer
  reconcile_interval: 5s
  storage_mode: memory
  store:
    path: indexer/indexes.db
    batch_size: 100
    batch_interval: 100ms
    queue_size: 10000
    block_cache_size: 134217728
```

Service assembly supplies direct Puller calls in standalone mode and a client in
distributed mode. The configuration schema owns supported settings; proposed
scan/spool tuning is not an active configuration contract. See
[storage design](04.storage.md) and [gRPC service](03.grpc.md).

## Costs and operational boundaries

Asynchronous index updates create eventual consistency. Rebuilds consume storage
reads and can exceed source retention. Failure is visible and checkpoint
advancement stops; automatic recovery is not yet implied by those protections.
Per-database health, lag and rebuild observability remain part of the recovery
and [observability](../../../../.agents/notes/proposed/architecture/2026-09-07-application-observability.md)
work. A completed recovery must demonstrate that query-ready state, index data,
and saved progress describe the same completed prefix.
