# Index Storage Design

Status: implemented storage contract; rebuild integration remains proposed

Memory and Pebble stores expose the same index operations so Query and template
matching do not depend on persistence. Memory storage provides synchronous local
updates; Pebble batches index mutations and completed Puller progress. Stored
progress must never acknowledge an index mutation that failed to commit.

## Storage contract

The [Store interface](../../../../internal/indexer/store/store.go) defines:

```go
type Store interface {
    Upsert(db, pattern, tmplID, docID string, orderKey []byte, progress string) error
    Delete(db, pattern, tmplID, docID string, progress string) error
    Get(db, pattern, tmplID, docID string) (orderKey []byte, found bool)
    Search(db, pattern, tmplID string, opts SearchOptions) ([]DocRef, error)

    DeleteIndex(db, pattern, tmplID string) error
    DeleteDatabase(db string) error
    SetState(db, pattern, tmplID string, state IndexState) error
    GetState(db, pattern, tmplID string) (IndexState, error)
    ListDatabases() ([]string, error)
    ListIndexes(db string) ([]IndexInfo, error)

    LoadProgress() (string, error)
    SaveProgress(progress string) error
    Failed() <-chan struct{}
    Err() error

    Flush() error
    Close() error
}
```

`SearchOptions` contains inclusive `Lower`, exclusive `Upper`, exclusive
`StartAfter`, and `Limit`. `DocRef` contains a document ID and encoded order key.
Index states are `healthy`, `rebuilding`, and `failed`. Index enumeration supplies
template identity, pattern, state, and document count for management/reconciliation.

Progress is the complete opaque Puller source/generation/sequence marker. It is
neither a single event ID nor a MongoDB resume token. `SaveProgress` places it in
the ordered write pipeline; a successful call does not by itself mean a Pebble
Sync has completed. An empty operation progress argument requests no checkpoint
update.

## Event completion and checkpoint ordering

The Indexer service processes Puller envelopes sequentially. For an event matching
multiple templates, it submits every template mutation with empty progress, then
calls `SaveProgress` only after all calls succeed. Initial/progress-only envelopes
and events producing no index mutations still complete their progress. A template
failure prevents that event's checkpoint from being submitted.

```text
Subscription.Next()
        |
        v
Apply all matching template mutations
        |
        | all accepted successfully
        v
SaveProgress(complete opaque marker)
        |
        v
Ordered Pebble writer
        |
        +-> earlier mutation batches already synced
        +-> remaining mutations and completed progress in one Sync batch
```

A mutation may commit before its event checkpoint. That window can cause replay
after a crash, which requires idempotent application. The reverse window is
prevented: the checkpoint cannot commit ahead of an earlier failed mutation.
There is one owner of completed source progress; unrelated concurrent callers
must not submit markers that skip unresolved work.

## Memory store

`mem_store.Store` uses database-isolated in-memory indexes with ordered B-trees
and document-ID lookup maps. Upsert, delete, and progress updates are synchronous.
`Flush` and `Close` are no-ops. `Failed()` returns nil and `Err()` returns nil
because this store has no asynchronous persistence worker.

Index data and progress disappear on process restart. The complete reconstruction
workflow is still owned by the
[Indexer recovery proposal](../../../../.agents/notes/proposed/architecture/2026-09-07-indexer-recovery-lifecycle.md).
An empty progress marker alone cannot restore pre-existing documents.

## Pebble store and layout

`persist_store.PebbleStore` owns one local Pebble DB. Its logical keys are:

```text
idx/<database>/<hash>/<orderKey>      -> document ID
rev/<database>/<hash>/<documentID>    -> previous order key
map/<database>/<hash>                 -> pattern | template ID
meta/state/<database>/<hash>          -> index state
meta/progress                        -> opaque aggregate Puller progress
```

The index hash is the complete 16-character hexadecimal xxHash64 of
`pattern + "|" + templateID`. Path components are escaped where required by the
key encoder; binary order keys preserve index range ordering. Reverse keys let
an upsert remove the prior ordered entry for the same document.

Pending operations are grouped by index and document, so later mutations to the
same pending document replace earlier ones. The worker swaps pending data and
completed progress together into its flushing batch. New requests enter the next
pending set while the worker synchronizes the current set. A checkpoint-only
batch is also written, even when the completed envelope made no index mutation.

Queued index deletions execute before the checkpoint-bearing batch. Their
individual deletes are not one transaction with that batch. If a deletion fails,
the old checkpoint remains the recovery boundary and later batches are fenced.
A successful event batch writes index entries, reverse entries, template mapping,
and selected progress together with `pebble.Sync`.

Search merges persisted data with flushing and pending operations, giving later
pending values precedence. This read visibility is useful for local index
queries but is not evidence that the corresponding checkpoint is durable.
`LoadProgress` similarly returns pending progress when present; after reopening
the store, only the committed `meta/progress` can be loaded. Callers needing
completed persistence must use `Flush` and check its result.

## Asynchronous failures and lifecycle

Any error applying a batch operation, removing an index, setting its checkpoint,
or synchronizing the batch becomes a sticky terminal writer error. `Failed()`
closes once and `Err()` retains the original error chain. Later batches do not
commit, and new upsert/delete/progress calls and progress loading return that
failure. `Flush` also returns the failure; a later checkpoint cannot hide it.

The service monitors `Failed` while waiting on `Subscription.Next`. A store
failure cancels the blocked read with the store cause and stops ingestion,
including when no further source event arrives. Health/lifecycle results report
the terminal error. The store does not retry a failed commit once and continue,
or silently treat disk-full as permission to advance progress.

`Flush` waits for pending operations, index deletions, checkpoint-only work, and
an in-flight batch. Its current timeout is the greater of five seconds and fifty
batch intervals. That timeout does not cancel a physical storage sync. `Close`
stops the worker, performs its final flush, joins it, and closes the DB while
returning the retained writer/close errors. This store's `Close` has no context
parameter; it does not promise a caller-controlled physical-sync deadline.

Read methods keep their existing individual result/error contracts. The terminal
writer signal is not a replacement for checking read errors, and does not imply
that every read method is a universal health check.

## Configuration and costs

```yaml
indexer:
  storage_mode: pebble
  store:
    path: indexer/indexes.db
    batch_size: 100
    batch_interval: 100ms
    queue_size: 10000
    block_cache_size: 134217728
```

The store path resolves through service configuration. Memory remains the default
storage mode. The default block cache is 128 MiB. Pebble reduces the need to keep
all index entries in Go memory, but cache, pending/flushing maps, and active
searches each consume memory; the cache setting is not a total RSS limit.

Indexer batching settings are separate from
[Puller admission and strict batch budgets](../puller/01.architecture.md#configuration-and-latency).
The current Indexer writer uses operation count to trigger flushing and a periodic
interval; it does not implement Puller's strict count/byte admission policy.
`queue_size` exists in Indexer configuration but does not establish a proven bound
on its pending maps. Do not infer a memory guarantee or a measured latency from
these settings. Throughput and read/write latency require workload measurements.

## Rebuild and observability work still proposed

The intended rebuild captures a durable source position before scanning,
marks the affected index unavailable, scans authoritative documents, applies
replay through a known cut, joins live processing, and persists completed data
and progress before marking the index healthy. Existing rebuild/reconciler
components are not yet connected into that full production lifecycle.

Persistent startup loads index data and progress; it still needs verified
reconstruction when data is missing, a template changes, a rebuild was interrupted,
or Puller history/generation validation fails. Retained replay alone cannot
reconstruct documents older than that history. These cases belong to
[Indexer recovery](../../../../.agents/notes/proposed/architecture/2026-09-07-indexer-recovery-lifecycle.md),
not to automatic repair claimed by this storage contract.

Write/read counters, batch duration and size, pending occupancy, disk use, and
per-index recovery health remain observability requirements. They are not
implemented metrics merely because the store exposes `Err` and `Failed`.
See [application observability](../../../../.agents/notes/proposed/architecture/2026-09-07-application-observability.md).
