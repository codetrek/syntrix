# Puller Service Architecture

**Date:** December 29, 2025
**Status:** Implemented
**Component:** Change Stream Puller (Fan-out Service)

## 1. Overview

The Puller is a standalone service that acts as a centralized fan-out layer between MongoDB and multiple event consumers. It watches MongoDB change streams, normalizes events, manages checkpoints, buffers events in PebbleDB, and distributes events to downstream consumers via gRPC streaming.

### 1.1 Design Goals

- **Single MongoDB Connection**: Minimize load on MongoDB by maintaining only one change stream connection per backend
- **Fan-out**: Distribute events to multiple independent consumers (Engine Index, Streamer, Trigger Service)
- **Reliability**: Ensure no event loss through checkpoint management and resume token persistence
- **Scalability**: Support horizontal scaling (see [future/001.shard-scaling.md](future/001.shard-scaling.md) for shard-based consumer scaling)
- **Observability**: Provide metrics and health checks for monitoring

## 2. Core Components

### 2.1 Change Stream Consumer

Maintains one native database-level MongoDB change stream per backend over its fixed physical collection allowlist. Capture opens directly through the Mongo client; the logically scoped `DocumentStore.Watch` API has a separate contract. Transient connection failures resume from the last admitted source checkpoint.

### 2.2 Event Normalizer

Converts MongoDB change stream events to internal event format, extracts database information, flattens nested document structures, and computes event hashes for deduplication.

### 2.3 Checkpoint Manager

Persists an opaque source checkpoint per backend. Its binding keeps a retained native position valid across process and connection replacement while rejecting a different source or capture scope.

| Checkpoint component | Meaning |
|---|---|
| Source | Stable configured backend name, physical database, and sorted physical collection name/UUID pairs |
| Capture contract | Versioned database watch with `UpdateLookup`, fixed collection scope, and lifecycle controls |
| Position | Complete BSON `resumeAfter` token, or an explicit bootstrap `startAt` timestamp |
| Excluded identities | Puller endpoint, local cache generation, event key, and local sequence |

Initial and idle positions share the ordered write queue with events. Each event record retains its own native token; a later batch high-water token cannot become that event's checkpoint. The last queued position and that batch's events commit atomically. Connection retries retain the process's last admitted checkpoint so a delayed disk commit cannot rewind capture.

These checkpoints currently belong to capture and cached records. Consumer `ProgressMarker` still maps backend names to EventIDs, and the gRPC wire format is unchanged. Source checkpoints in consumer progress, processed-versus-received client state, cache-miss source replay, cache ordering, publication timing, before-images, and the 100-events/10ms cache target remain deferred. The [source checkpoint decision](../../../../.agents/notes/implemented/architecture/2026-09-08-puller-source-checkpoints.md) records their costs and constraints.

### 2.4 Event Buffer (PebbleDB)

Persists versioned event/checkpoint records locally for replay, using the existing ordered event keys. Record reads and iterators expose the associated source checkpoint. An explicit cache format marker rejects nonempty legacy caches; deployment requires deliberate replacement, with no inferred migration or automatic reset. A writer failure remains visible to later operations and repeated close calls.

### 2.5 gRPC Server

Exposes server-side streaming API for consumers. Streams merged events from all backends. Applies catch-up coalescing when consumer is behind threshold. Consumer manages its own progress (Puller does not store it).

## 3. Canonical Event Schema

**IMPORTANT**: This section defines the Puller event schema. For the complete field naming conventions across all system components, see [Field Naming Conventions](../002_field_naming.md).

### 3.1 JSON Wire Format

```json
{
  "change_event": {
    "eventId": "unique-event-id",
    "database": "database-id",
    "mgoColl": "collection-name",
    "mgoDocId": "document-id",
    "opType": "insert",
    "fullDoc": { },
    "updateDesc": {
      "updatedFields": { },
      "removedFields": ["field1"],
      "truncatedArrays": []
    },
    "clusterTime": { "T": 1234567890, "I": 1 },
    "txnNumber": null,
    "timestamp": 1234567890000,
    "backend": "backend-name"
  },
  "progress": "opaque-progress-marker"
}
```

### 3.2 Field Specifications

| Field | JSON Key | Type | Required | Notes |
| ----- | -------- | ---- | -------- | ----- |
| **Wrapper** | | | | |
| Change Event | `change_event` | object | Yes | The actual event payload |
| Progress | `progress` | string | Yes | Opaque marker for resuming |
| **Change Event** | | | | |
| Event ID | `eventId` | string | Yes | Unique identifier for deduplication |
| Database ID | `database` | string | Yes | Derived from `fullDoc.database` |
| Mongo Collection | `mgoColl` | string | Yes | Mongo collection name |
| Mongo Document ID | `mgoDocId` | string | Yes | Mongo `_id` |
| Operation Type | `opType` | string | Yes | lowercase: "insert", "update", "replace", "delete" |
| Full Document | `fullDoc` | object | No | `storage.StoredDoc` shape. Required for insert/update/replace |
| Update Description | `updateDesc` | object | No | Present for update operations |
| Cluster Time | `clusterTime` | object | Yes | MongoDB timestamp {T, I} |
| Transaction Number | `txnNumber` | int64 | No | Present if in transaction |
| Timestamp | `timestamp` | int64 | Yes | Unix milliseconds |
| Backend | `backend` | string | No | Backend identifier |

### 3.3 Operation Types

All operation types are **lowercase**:

- `"insert"` - New document created
- `"update"` - Document fields updated
- `"replace"` - Document replaced entirely
- `"delete"` - Mongo document physically removed; ignored during business-event conversion

Syntrix logical deletion is an update or replacement carrying a tombstone
(`deleted=true`, `data={}`, retained metadata). It remains a business deletion
notification. See [deletion semantics](../core/storage/03.stores.md#document-deletion-and-physical-cleanup).

### 3.4 Full Document Contract

The `fullDoc` field MUST adhere to the `storage.StoredDoc` JSON schema.
For `update` and `replace` operations, the Puller requires `UpdateLookup` to be enabled on the change stream, ensuring `fullDoc` is always present. Events missing `fullDoc` for these operations will be rejected.

## 4. Event Flow

### 4.1 Normal Flow

1. MongoDB emits change event
2. ChangeStreamConsumer receives event
3. EventNormalizer converts to internal format
4. Buffer admits the event and its source checkpoint to the batch queue
5. The background writer commits queued records and their final checkpoint atomically
6. Live publication follows admission and can precede step 5
7. Consumer saves its progress marker after successful processing

### 4.2 Startup Recovery Flow

1. Storage initialization prepares data/system namespaces on writable document backends; Puller starts
2. Buffer validates its format and loads the committed source checkpoint
3. Capture reads the configured physical collection UUIDs; every allowlisted collection must already exist, including externally managed scopes that storage initialization does not provision
4. A saved checkpoint must match the source and capture scope before its native position is used
5. Open the cursor using the saved position; fresh `from_now` requests an empty first batch, while `from_beginning` selects `startAt (1, 1)` and requires available source history
6. Verify source identity again after opening
7. For fresh capture, persist the initial server token or explicit start boundary before reading events

### 4.3 Gap Detection and Recovery

1. Long event intervals (default threshold: 5 minutes) produce diagnostic warnings; inactivity alone does not prove lost history
2. Invalid checkpoints, changed source/scope, lifecycle invalidation, and unavailable native history stop the affected capture
3. Recovery retains its checkpoint and reports the failure; it never clears progress to open a fresh stream
4. Consumer-visible history errors and coordinated rebuild/resynchronization remain deferred

## 5. gRPC API

### 5.1 Service Definition

A single gRPC server handles all backends. Consumers subscribe to a merged event stream without knowing which backend events come from.

```protobuf
service PullerService {
  // Subscribe to merged event stream from all backends
  rpc Subscribe(SubscribeRequest) returns (stream Event);
}

message SubscribeRequest {
  string consumer_id = 1;          // for logging/monitoring only
  string after = 2;                // progress marker: return events after this (exclusive)
                                   // empty = start from current head (no historical events)
  bool coalesce_on_catch_up = 3;   // enable catch-up coalescing
}

message Event {
  string id = 1;                   // unique event ID
  string database = 2;
  string collection = 3;
  string document_id = 4;
  string operation_type = 5;       // insert, update, replace, delete
  bytes full_document = 6;
  bytes update_description = 7;
  ClusterTime cluster_time = 8;    // MongoDB cluster timestamp
  int64 timestamp = 9;             // Unix milliseconds
  string progress = 10;            // current progress marker (opaque, save this)
}

message ClusterTime {
  uint32 t = 1;                    // seconds since epoch
  uint32 i = 2;                    // increment within second
}
```

### 5.2 Progress Marker

The `progress` field in each event is an opaque string that encodes the current position across all backends. Consumers should:

1. Save the `progress` field from the last successfully processed event
2. Pass it as `after` when reconnecting to resume from that point
3. Not attempt to parse or understand its internal structure

### 5.3 Consumer States

- **Real-time**: Position near head, events forwarded as-is
- **Catching-up**: Position behind by `catch_up_threshold`, optional coalescing applied

## 6. Key Design Decisions

### 6.1 PebbleDB Event Buffer

We use PebbleDB as a local event buffer because:

- Durable storage survives Puller restart
- Supports multiple consumers at different positions
- Ordered key storage enables efficient range scans
- LSM tree optimized for write-heavy workloads
- Configurable size limit with automatic cleanup

### 6.2 At-Least-Once Delivery

- Atomic event/checkpoint persistence protects capture restart; publication can precede the commit, so this alone does not establish end-to-end at-least-once delivery
- Consumers must be idempotent (handle duplicate events)
- Events may be delivered multiple times on retry, reconnect, etc.

### 6.3 Catch-up Coalescing

When a consumer falls behind by more than `catch_up_threshold` events:

- Multiple updates to the same document are merged
- insert + physical Mongo delete = skip (raw storage operations; a logical tombstone is an update/replace)
- Reduces catch-up time for slow consumers
- Consumer can disable via `coalesce_on_catch_up: false`
