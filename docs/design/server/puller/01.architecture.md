# Puller Service Architecture

Status: implemented

Puller owns one MongoDB change stream and one durable Pebble event log per
configured backend. Indexer, Streamer, and Trigger consume the same subscription
contract through direct calls or gRPC. Live delivery uses the committed batch
already in memory; retained-history catch-up reads Pebble.

## Delivery and ownership

```text
MongoDB Change Stream
         |
         v
 Reader / normalizer
         |
         v
 Bounded admission queue
         |
         v
 Single backend committer -----> Pebble event log
         |
         | Sync commit succeeds
         v
 Safe view + ordered publication
         |
         +----------------------+----------------------+
                                |                      |
                                v                      v
                       Live queue (memory)     Catch-up (Pebble)
                                |                      |
                                +-----------+----------+
                                            |
                                            v
                                  Shared subscription
                                            |
                                      Local / gRPC
```

The committer owns appends, source-boundary initialization, retention, continuity
invalidation, and shutdown. One batch atomically stores event records, stable
identity mappings, the committed position, and the last accepted MongoDB resume
token. Only a successful synchronous commit publishes the corresponding safe
read view and invokes the ordered, nonblocking subscription coordinator.

This ordering ensures a consumer never receives progress beyond the durable
log. A crash after commit but before publication is recoverable through replay.
A crash before commit resumes from the prior durable source boundary while that
upstream history remains available. Consumers still need idempotent processing:
delivery completion does not acknowledge their business side effects.

`Buffer.Enqueue` freezes input and means admission, not persistence. Credits
remain charged through batching, synchronous commit, and the publication
callback. The Reader can enqueue multiple events so a batch can form before its
commit completes. `Flush` fences all admissions before the call; ingestion uses
that fence before reopening MongoDB so a reconnect cannot resume behind an
unfinished admitted batch.

## Source identity, event identity, and order

Each backend requires an operator-assigned `source_id`. Keep it stable when the
same source is restarted or its storage connection endpoint changes. Assign a
new identity when binding to different data. The log also records the MongoDB
database and sorted collection scope; reopening it with a changed identity or
scope fails explicitly.

| Value | Meaning |
|---|---|
| Source ID | Stable identity of the configured upstream data source |
| Generation | One continuous event-log history; generated at empty-store initialization |
| Sequence | Monotonically increasing committed ingestion position within a generation |
| Event ID | `v1-` plus SHA-256 of versioned, length-delimited source ID and full BSON event resume token |
| Format version | Version of the stored state or opaque progress encoding |

Event identity and position are separate. Retained duplicates reuse the original
record and position; distinct complete upstream identities receive distinct
records. The log verifies raw identity bytes when resolving an identity mapping
and does not regress its resume token for a retained duplicate. Deduplication
covers pending batches and retained records; it does not promise deduplication
across deliberately discarded history.

The logical key layout is:

```text
meta/state
  source ID, scope, generation, committed position, discarded position,
  resume token or initial operation time, retained bytes, continuity state

event/<generation>/<sequence>
  immutable normalized event and complete upstream identity

identity/<generation>/<event ID>
  original sequence and upstream identity
```

Sequence keys preserve numerical order. MongoDB cluster time remains event
metadata; timestamps, document IDs, and hashes do not determine replay position.
There is no total-order guarantee across independent sources.

## Initial source boundary and recovery

Before opening a first watch, Puller durably anchors its initial boundary:

- `from_now` obtains a session operation time from MongoDB and saves it before
  the watch becomes ready. A restart before the first event reuses that boundary.
- `from_beginning` reads the earliest retained entry in `local.oplog.rs` and saves
  its timestamp. The MongoDB account must have permission to read that collection.
  This means the beginning of retained oplog history, not a scan of all documents.

The first event batch replaces the initial operation time with its resume token.
Later starts and reconnects use the saved token. Loading state, decoding an
event, normalization, or persistence failure stops progress and preserves the
error chain. Transient source reconnection is bounded by context and uses the
last flushed boundary. Authoritative history-loss errors persist discontinuity
and stop publication; a long interval without events is not proof of loss.

An affected backend reports failure and terminates aggregate subscriptions.
Unaffected backend logs remain intact. Indexer, Streamer, and Trigger receive the
failure rather than acknowledging later work across the missing prefix.

## Safe replay and retention

Pebble can expose an in-flight batch internally before its synchronous commit
returns. Replay therefore reads a snapshot published only after Sync succeeds.
The snapshot and metadata agree on the committed and discarded positions.

`ReadPage` validates source, generation, range, and sequence continuity in that
safe view, copies a bounded page, and releases its iterator and view lease before
network delivery. Retention deletes a contiguous sequence prefix and its identity
mappings in one batch with the discarded boundary and logical byte accounting.
Physical LSM file size is not the eviction progress measure: compaction and short
snapshot leases can delay physical reclamation.

If the log retains `901..1042`, checkpoint `900` is valid, `899` is expired, and
`1043` is ahead. A later page can fail if a slow subscriber falls behind retention;
it never silently skips to the new oldest event.

## Subscription and wire contract

The public Go interface is:

```go
Subscribe(context.Context, events.SubscribeOptions) (events.Subscription, error)

// SubscribeOptions: ConsumerID, After, CoalesceOnCatchUp
// Subscription: Next(context.Context) (*events.PullerEvent, error), Close() error
```

The first `Next` returns a progress-only envelope identifying the effective start.
An empty `After` captures the current published heads; it requests future events,
not retained history. A supplied marker must name every configured source with
valid generation and sequence. Omitted sources, added sources, malformed cursors,
unknown formats, and expired history are explicit failures.

Progress is a versioned, opaque base64url JSON marker containing independent
source/generation/sequence positions. Consumers save the complete string only
after successful processing and pass it back as `After`. They must not infer
position from `EventID` or parse the marker as a MongoDB resume token.

The protobuf fields remain unchanged. `PullerEvent` contains an optional
`change_event` and `progress`; nil change is a meaningful progress-only message.
After validating the initial envelope, gRPC sends these response headers:

```text
syntrix-puller-subscription: ready
syntrix-puller-initial-progress: <opaque effective start marker>
```

The client anchors reconnection to this start even if the transport breaks before
the first body message. It advances reconnect progress only after a successful
`Next` return and shares one connection across subscriptions. Normal transport
retries preserve the cursor; domain failures are returned to the caller.

| Domain reason | Meaning | gRPC status |
|---|---|---|
| `INVALID_CURSOR` | Malformed cursor or invalid range | InvalidArgument |
| `UNKNOWN_SOURCE` | Unknown or omitted source | InvalidArgument |
| `POSITION_AHEAD` | Position beyond the published frontier | InvalidArgument |
| `GENERATION_MISMATCH` | Cursor refers to a different history | FailedPrecondition |
| `HISTORY_EXPIRED` | Required prefix has been evicted | FailedPrecondition |
| `CONTINUITY_LOST` | Upstream history is no longer continuous | FailedPrecondition |
| `UNSUPPORTED_FORMAT` | Unrecognized stored or protocol format | FailedPrecondition |
| `STORAGE_FAILURE` | Durable log or replay operation failed | Internal |
| `SOURCE_UNAVAILABLE` | Source cannot continue | Unavailable |
| `OVERLOADED` | Admission or encoded-record limit exceeded | ResourceExhausted |

Typed local errors retain their cause. gRPC uses `google.rpc.ErrorInfo` with
`domain = syntrix.puller`, the reason above, and safe backend/source/generation
and position metadata. Raw resume tokens and document bodies are not diagnostics.

The [subscription design](02.adaptive-consumption.md) owns live/replay handoff,
coalescing, admission, and consumer progress semantics.

## Configuration and latency

This excerpt uses integer byte counts for memory/page budgets:

```yaml
puller:
  backends:
    - name: default_mongo
      source_id: default-mongo
      collections: [documents]
  buffer:
    path: puller/events
    max_size: 10GiB
    batch_size: 100
    batch_interval: 100ms
    queue_size: 10000
    queue_bytes: 67108864
    batch_bytes: 16777216
  grpc:
    max_connections: 100
    channel_size: 10000
    heartbeat_interval: 30s
  consumer:
    catch_up_threshold: 100000
    coalesce_on_catch_up: true
    queue_bytes: 67108864
    page_size: 100
    page_bytes: 16777216
  cleaner:
    interval: 1m
    retention: 1h
  bootstrap:
    mode: from_now
```

`batch_size` and `batch_bytes` are strict per-batch maxima. `batch_interval` is
the oldest admitted event's batching deadline; new arrivals do not reset it.
They are configurable, with defaults of 100 events and 100ms. A full batch,
byte boundary, flush fence, or shutdown can submit earlier. Existing work and
physical sync time can extend actual delivery latency beyond the interval.

Byte/page settings must be positive; `batch_bytes` cannot exceed write
`queue_bytes`, and `consumer.page_bytes` must accommodate `buffer.batch_bytes`.
A smaller `consumer.queue_bytes` may intentionally send larger live events through
replay. The client receive limit defaults to 64 MiB and is configurable through
`client.NewWithConfig`; it bounds accepted protobuf messages.

`queue_size` and `queue_bytes` bound each backend's admitted work through
publication. Oversized individual records fail explicitly. Byte limits account
for encoded records and identity metadata; they are not a promise that total
process RSS equals that budget. Driver buffers, temporary encoding, replay pages,
subscriber queues, and Pebble caches also consume memory. `max_size` limits
retained logical log bytes; cleaner retention and interval govern prefix expiry.

Reducing the batch interval lowers sparse-traffic waiting and can increase
synchronizations per event. Live consumers avoid a Pebble read and decode round
trip. The durability guarantee adds batching and sync latency to change delivery,
not an explicit Puller wait to the REST write acknowledgement.

## Shutdown and operator-controlled reset

Close stops admission and drains accepted work. Waiting producers receive
cancellation, close, or the stored failure. A shutdown deadline can expire while
a physical sync still runs; its writer retains ownership and eventually closes
the DB. A timeout does not prove the write did not commit. Never concurrently
reuse or remove that log until the owning process and storage operation stop.

Unversioned nonempty logs, changed sources/scopes, unsupported cursors, and
persisted discontinuity are refused. There is no automatic legacy-key conversion
or silent checkpoint deletion. Old timestamp/hash keys cannot establish the
original ingestion order.

For an intentional reset or incompatible upgrade, the operator must:

1. Stop ingestion and affected consumers, and ensure log ownership has ended.
2. Preserve the old log and consumer checkpoints for investigation or an
   authoritative migration. Choose the required rebuild/reconciliation scope.
3. Provision an empty backend log with the correct stable source identity;
   initialization creates a new generation. Choose the bootstrap mode explicitly.
4. Rebuild or reconcile derived state and external effects, then establish new
   consumer checkpoints against that generation before declaring recovery complete.

Starting fresh does not reconstruct documents older than the retained oplog or
historical Webhook side effects. Automated Indexer rebuild, durable Streamer
restart, and external-client resynchronization remain separately owned work in
[Indexer recovery](../../../../.agents/notes/proposed/architecture/2026-09-07-indexer-recovery-lifecycle.md),
[Streamer progress](../../../../.agents/notes/proposed/architecture/2026-09-07-streamer-durable-progress.md),
and [client resume](../../../../.agents/notes/proposed/feature/2026-09-07-realtime-client-resume.md).
