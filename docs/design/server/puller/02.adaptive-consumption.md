# Puller Subscription Delivery

Status: implemented

Local and gRPC consumers share one subscription state machine. Retained history
comes from bounded Pebble pages; live events come directly from committed memory
batches. The [log architecture](01.architecture.md) owns source identity,
persistence, safe views, errors, and configuration defaults.

## Registration and handoff

Registration, head capture, and committed-batch publication share the coordinator
lock. Each subscription receives a unique internal registration ID; `ConsumerID`
is a diagnostic label, so duplicate labels cannot replace or close one another.

A registration captures a committed cut for every source. Empty `After` starts
at those cuts. A saved marker starts at its validated positions. The initial
`Next` always returns the effective start as a progress-only envelope.

```text
Consumer start = 100            Cut H = 120
                                   |
Pebble replay:    101 ... 120        |
Live memory:                       | 121 122 123 ...
                                   |
Delivery:        101 ... 120 121 122 123 ...
```

Events through the cut belong to replay. Newly committed events after the cut
enter the live queue while replay runs. One `Next` loop drains replay before live
records, with independent positions per source. Sequence continuity checks
prevent an overlap from becoming a duplicate advancement or a gap.

## Slow subscribers

```text
REGISTER -> INITIAL PROGRESS -> REPLAY -> LIVE
                                  ^        |
                                  |        | queue overflow or missing sequence
                                  +--------+

Any state -> TERMINAL ERROR / CANCELED -> registration removed
```

Live queues are bounded by `grpc.channel_size` and `consumer.queue_bytes` per
subscription. The committer never waits for network delivery. Overflow clears
the incomplete queue and records the need for replay. After any already prepared
page has been delivered, the sender captures a new cut and resumes from its last
successfully returned progress. Subsequent commits queue beyond that cut.

Replay reads at most `consumer.page_size` events and `consumer.page_bytes` encoded
payload bytes in each page. Snapshot leases end before transport delivery.
History expiry during a long catch-up is an explicit terminal result. Retention
therefore bounds recoverable lag, even though overflow alone does not require a
transport disconnect.

`grpc.max_connections` limits active subscriptions, including the shared local
service; it counts streams, not TCP connections. The gRPC adapter also bounds its
active handlers. Cancellation and all terminal paths release registration
capacity. Over-admission returns `OVERLOADED`.

## Coalescing policy

Exact delivery is the default per request. Coalescing requires both
`SubscribeOptions.CoalesceOnCatchUp` and server `consumer.coalesce_on_catch_up`.
During replay, `consumer.catch_up_threshold` selects coalescing when that source's
remaining distance to the fixed cut reaches the threshold. It does not currently
move a live subscriber into replay before overflow; the remaining policy is
owned by the [lag-trigger proposal](../../../../.agents/notes/proposed/bug-fix/2026-09-07-puller-admission-and-catch-up-settings.md).

Coalescing is bounded to a replay page and produces the final relevant state for
each document. A terminal delete remains visible, including insert-then-delete,
so retrying after a partially delivered page converges correctly. Intermediate
transitions can disappear, so consumers needing every transition must not opt in.

A coalesced page's progress advances across the page only after all of its output
has been returned. Earlier output carries the prior progress and may be repeated
after reconnect. An empty output window still returns progress. Consumers must
handle a nil change as a progress-only message, including initial and heartbeat
envelopes, rather than assume every envelope contains a document.

## Processing acknowledgement and failures

`Next` completing establishes delivery to its caller. It does not establish that
an index write, task publication, gateway send, or external effect succeeded.
Each consumer saves only its last successfully processed aggregate progress.
Concurrent work can acknowledge only a contiguous completed prefix.

The direct consumers preserve this distinction:

- Indexer stops on transformation, index-application, checkpoint, or upstream
  failure. Its persistent store retains asynchronous batch failure and fences
  later checkpoint saves.
- Streamer advances in-memory progress after processing and closes its owned
  gateway streams on terminal upstream failure. Restart persistence remains the
  [durable progress proposal](../../../../.agents/notes/proposed/architecture/2026-09-07-streamer-durable-progress.md).
- Trigger carries progress-only envelopes and terminal errors through its
  watcher. Evaluation/publication failure stops progress; checkpoint-save failure
  cancels consumption. Its saver is canceled before being joined when upstream
  ends. Durable scheduling/outbox remains the
  [Trigger idempotency proposal](../../../../.agents/notes/proposed/architecture/2026-09-07-trigger-delivery-idempotency.md).

Errors preserve their cause locally and domain reason over gRPC. A terminal
storage, format, or continuity error is not retried indefinitely as a transport
failure. Subscription close is idempotent; cancellation removes exactly that
registration and releases pending pages and queued references.

## Costs and validation

Memory live delivery avoids an additional Pebble read and decode for consumers
that keep up. Slow consumers pay replay I/O and decoding costs. Queue budgets,
page budgets, batch budgets, and retained-history size are separate because they
have different owners and release points.

Correctness tests cover commit blocking/failure, replay/live registration races,
overflow during replay, equal-timestamp events, retained duplicates, invalid
markers, retention, independent sources, cancellation, and local/gRPC parity.
Performance must be measured with sparse, sustained, burst, and slow-consumer
loads; a batch interval alone is not an end-to-end latency guarantee.
