# Query Engine and Indexer Integration Design

**Date:** January 11, 2026
**Status:** Design Draft
**Component:** Query Engine + Indexer Integration

## 1. Overview

This document designs the integration between Query Engine and Indexer service.

**Core Principles:**
1. Indexer is a **required dependency** for indexed queries; unsupported predicates do not trigger a storage-scan fallback
2. **Standalone mode only** (`--standalone`): direct in-process calls allowed
3. **Distributed mode** (default, including `--all`): must use gRPC, even if services are in same process

## 2. Design Rationale

### Why Indexer is Required

1. **Performance policy**: Filtered or ordered queries use Indexer, except unordered ID-only lookups; unfiltered, unordered listing uses Store directly
2. **Clear architecture**: Explicit dependencies, no implicit degradation
3. **Operational visibility**: Indexed queries fail explicitly if Indexer is unavailable
4. **Simplified code**: No fallback logic, reduced complexity

### Filter Planning

Dropping an unsupported predicate can broaden a result and cause clients that
update or delete the returned documents to affect unintended records. Query must
reject an indexed query when an operator cannot be translated, before submitting
any index search.

| Query shape | Execution contract |
|---|---|
| No filters and no ordering | Store query |
| All filters are `id ==` or `id in`, without ordering | Store query |
| Other queries using `==`, `>`, `>=`, `<`, or `<=` | Index planning, subject to existing index and plan requirements |
| Indexed query containing `!=`, `in`, `contains`, or an unknown operator | Invalid query; no index search or partial result |

The planner's invalid-query error identifies the operator without exposing its
field or value. It maps to gRPC `InvalidArgument` and HTTP 400 `BAD_REQUEST`.
REST request validation rejects unknown operators earlier with the generic
message `Invalid query parameters` and HTTP 400 `BAD_REQUEST`. Shared filter
syntax remains available to Store, conditional writes, and realtime consumers;
the restriction belongs to indexed Query planning. This operator check does not
establish support for every predicate combination. Existing request-validation
and missing-Indexer checks retain their precedence over planning.

The [rejection decision](../../../../.agents/notes/implemented/bug-fix/2026-09-11-query-unsupported-filter-rejection.md)
records the trade-off. [Full indexed filter execution](../../../../.agents/notes/proposed/bug-fix/2026-09-07-indexed-query-filter-semantics.md)
owns the deferred operator strategies, ordering, and index representation work.

Indexer intersects repeated equality and range conditions on each usable index
field. Conditions are order-independent: equalities must agree and satisfy every
range, the strongest lower and upper bounds win, and contradictory bounds yield
an empty result. Ascending and descending fields use the existing encoded-value
semantics. See [same-field constraints](../indexer/02.index.md#same-field-constraints)
for the contract. Existing index selection and field-placement requirements
remain; this does not establish complete cross-field predicate evaluation.

### Why Distributed Mode Must Use gRPC

1. **Consistency**: Behavior is the same regardless of deployment topology
2. **Testability**: Dev environment behaves the same as production
3. **Simplified code**: No "same process or cross-process" branching logic

## 3. Architecture

### 3.1 Mode Determination

| CLI Flag | Config | Mode | Query → Indexer |
|----------|--------|------|-----------------|
| `--standalone` | - | Standalone | Direct call |
| - | `deployment.mode: standalone` | Standalone | Direct call |
| `--all` | - | Distributed | gRPC |
| `--query` | - | Distributed | gRPC |
| (default) | - | Distributed | gRPC |

### 3.2 Standalone Mode (`--standalone`)

```
┌─────────────────────────────────────────────────────┐
│                   Single Process                     │
│                                                      │
│  API ──► Query ──direct call──► Indexer ──► Puller  │
│            │                       │                 │
│            │                       ▼                 │
│            └───────────────────► Storage             │
└─────────────────────────────────────────────────────┘
```

### 3.3 Distributed Mode (default, including `--all`)

```
┌─────────────────┐      gRPC       ┌─────────────────┐
│  API Gateway    │ ───────────────►│  Query Service  │
└─────────────────┘                 └────────┬────────┘
                                             │ gRPC (required)
                                             ▼
                                    ┌─────────────────┐
                                    │ Indexer Service │
                                    └────────┬────────┘
                                             │ gRPC
                                             ▼
                                    ┌─────────────────┐
                                    │ Puller Service  │
                                    └─────────────────┘
```

**Note**: Even with `--all` (all services in same process), Distributed mode must communicate via gRPC.

## 4. Interface Changes

### 4.1 Query Engine

```go
// Before: Indexer optional
func New(storage storage.DocumentStore) *Engine

// After: Indexer required
func New(storage storage.DocumentStore, indexer indexer.Service) *Engine
```

### 4.2 Query Package

```go
// Before
func NewService(store storage.DocumentStore) Service

// After
func NewService(store storage.DocumentStore, idx indexer.Service) Service
```

### 4.3 Error Types

| Error | Meaning |
|-------|---------|
| `ErrIndexerRequired` | Indexer not configured |
| `ErrNoMatchingIndex` | No matching index for query |
| `ErrIndexRebuilding` | Index is rebuilding |
| `ErrIndexNotReady` | Index not ready |
| `ErrInvalidQuery` | An indexed filter operator has no supported translation |

## 5. Configuration

### 5.1 New Config Fields

```yaml
gateway:
  indexer_service_url: ""  # Indexer gRPC address (required for Distributed mode)
```

### 5.2 Startup Commands

```bash
# Standalone - direct in-process calls
syntrix --standalone

# Distributed - all services, but must use gRPC between them
syntrix --all  # requires gateway.indexer_service_url for Query

# Distributed - Query only, requires Indexer gRPC address
syntrix --query  # requires gateway.indexer_service_url
```

## 7. Risks and Mitigations

| Risk | Mitigation |
|------|------------|
| Indexer down causes query unavailability | Multi-replica deployment + health checks |
| Query fails during index rebuild | Return clear error, client retry |
| Query fails with no matching index | Clear error message, guide to create index |
