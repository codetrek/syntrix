# Unified Server and Service Lifecycle

Status: implemented lifecycle with separate network-policy requirements

`internal/server` owns shared HTTP and gRPC listeners. Gateway routes and service
transport adapters register before the listeners start. `internal/services`
constructs components, establishes source readiness, starts consumers, and owns
shutdown. A listener being open does not prove that its event sources are ready.

## Why centralized registration

Separate listener construction originally duplicated ports, timeout policy,
logging, and shutdown. Central registration gives shared network configuration
one owner while keeping authentication, authorization, request validation, and
service-specific behavior with their modules.

```text
Gateway routes ----------+
Query transport ---------+--> registration --> unified HTTP / gRPC listeners
Puller gRPC adapter -----+
Other service adapters --+

Service Manager
    |
    +-> component construction and dependencies
    +-> durable source readiness
    +-> listener launch
    +-> consumer startup
    +-> cancellation and shutdown
```

The Puller transport adapter exposes the shared subscription implementation; it
does not own a second source reader, event fan-out, or listening socket.

## Startup ordering

`Manager.Start(bgCtx) error` first starts a local Puller when one is configured.
Puller returns successfully only after every backend has established its durable
resume/initial-operation-time boundary and opened its change stream. Failure or
cancellation returns before event consumers start. This prevents a consumer's
current-head subscription from being treated as ready before the source has a
recoverable starting position.

The manager then launches the unified server before starting Streamer and Indexer.
Distributed deployments can route colocated consumers through that server, so
its serving loop must be launched before their transport connection attempts.
Streamer and Indexer startup errors return synchronously. Realtime background
registration, Trigger evaluator/delivery, and deletion workers start afterward.
Those workers retain their existing asynchronous error reporting; a successful
manager return does not certify that every later background task will succeed.

```text
Manager.Init: construct components and register transports
        |
        v
Manager.Start: Puller durable boundary + watch readiness
        |
        v
Launch unified server
        |
        v
Start Streamer, then Indexer
        |
        v
Launch remaining background workers
```

The unified server's serving loop runs asynchronously and logs its runtime
failure. Launching that loop is not a separate synchronous listener-bind
readiness acknowledgement.

## Failed startup and shutdown ownership

The caller owns `bgCtx` and must cancel it and call `Manager.Shutdown` when
synchronous startup returns an error. The CLI follows that contract: it cancels
the signal-backed background context, creates an independent cleanup context
using `Server.ShutdownTimeout`, calls shutdown, and then reports the startup
failure. The original canceled context cannot serve as the cleanup deadline.

Normal signal shutdown follows the same cancellation-then-cleanup order. The
manager stops Streamer-owned subscriptions and closes Puller transport streams
before waiting for gRPC graceful shutdown. It waits for workers within the
provided deadline, then closes PubSub, the Puller log, Indexer, and storage
resources in their ownership order. Shutdown failures remain logged.

A Puller shutdown deadline can expire while physical Sync still owns its DB and
batch. Neither failed startup nor timeout authorizes concurrent reuse or removal
of those files. See the [Puller shutdown contract](../puller/01.architecture.md#shutdown-and-operator-controlled-reset).

## Network boundaries and remaining design

`server.Service` exposes registration, `Start`, `Stop`, and route/middleware
accessors. Handler registration must precede startup. `Start` serves until failure
or cancellation; `Stop` drains or terminates listeners within its supported
shutdown behavior.

Global transport concerns belong to the server; endpoint authentication,
authorization, and service validation remain local to business modules. The
[requirements](00.requirements.md) and [detailed design](02.overall-design.md)
also describe desired middleware/telemetry policy; those requirements do not by
themselves establish that every observability integration has shipped.
