# Streamer Architecture

**Date:** January 3, 2026
**Status:** Design Draft
**Component:** Streamer Internal Architecture

## 1. Overview

Streamer matches business events to subscriptions and routes each result to the
Gateways holding interested clients. Puller owns source ingestion; Gateways own
client connections.

## 2. High-Level Architecture

```text
Puller --> Ingestion --> Business events --> Matching --> Routing --> Gateways
                                               ^                         |
                                               |                         v
                                      Subscription Manager            Clients
                                               ^
                                               |
                                      Gateway registrations
```

### 2.1 Key Design Decisions

| Decision | Rationale |
| --- | --- |
| Direct gRPC streaming | CEL predicates and fine-grained subscriptions exceed ordinary MQ topic routing; direct transport avoids an extra hop and a separate broker's operational cost |
| In-memory subscriptions with re-registration | Gateways own client interest, rebuild registrations after disconnect, and avoid database/Redis access during matching |

The transport alternative is NATS/Kafka. Representing millions of individual
queries as topics would increase control-plane state without providing CEL
matching. Streamer therefore owns matching and fan-out together.

## 3. Component Design

### 3.1 Ingestion Layer

- Receive and decode normalized MongoDB events from Puller.
- Convert source changes to business events before matching.
- Preserve received order among emitted business events.

| Source event | Business event |
| --- | --- |
| Insert carrying a live document | Create |
| Update/replace carrying a tombstone | Delete with that tombstone |
| Replace carrying a live document | Create, including recreation at a tombstoned path |
| Update carrying a live document | Update |
| Physical delete, including TTL cleanup | None |

Tombstones retain reference/metadata and contain `deleted=true`, `data={}`.
Physical cleanup must not produce a second business delete. See
[Document Deletion and Physical Cleanup](../core/storage/03.stores.md#document-deletion-and-physical-cleanup).

### 3.2 Subscription Manager

| Responsibility | Design |
| --- | --- |
| Lifecycle | Register, deregister, and expire subscriptions through heartbeat/TTL |
| Exact lookup | Trie or inverted index for collection and document-ID equality |
| Predicate lookup | Compiled CEL expressions; Bloom filter or bitset pre-filtering remains an optimization option |
| Ownership | Gateways restore their active subscriptions after reconnect |

### 3.3 Matching Engine

```text
Business event
    +--> Collection + document-ID lookup --+
    +--> CEL predicate evaluation --------+--> (GatewayID, SubscriptionID) matches
```

- Exact lookup targets O(1) or O(log N); broad queries use CEL evaluation.
- Delete predicates receive the tombstone's retained metadata and cleared data.
- Former business-field values require a separate historical-image capability.

### 3.4 Routing & Fan-out

| Concern | Design |
| --- | --- |
| Fan-out | Group matching subscriptions by Gateway and send one event with their IDs |
| Connection state | One active stream per Gateway connection |
| Batching option | Micro-batches below 1 ms when throughput justifies them |
| Backpressure decision | Bounded buffering is preferred; overflow requires a drop/disconnect policy |

## 4. Data Flow

### 4.1 Data Flow Architecture

Both deployment modes share one local stream abstraction:

```text
Puller --> Ingestion --> Matching --> Routing --> Local stream
                                                     |
                       +-----------------------------+-------------------+
                       v                                                 v
                In-process consumer                               gRPC adapter
                                                                         |
                                                                    gRPC network
                                                                         |
                                                                  Remote stream client
                                                                         |
                                                                    Remote consumer
```

The adapter owns protocol conversion; subscription and event semantics remain
shared between local and remote consumers.

### 4.2 Event Processing Steps

| Step | Example or responsibility |
| --- | --- |
| Register | Gateway subscribes to `chat_id=1` |
| Ingest | Puller supplies an insert containing `{chat_id: 1, text: "hi"}` |
| Convert | Produce a business create; stop physical cleanup before matching |
| Match | Evaluate `chat_id=1` and identify interested subscriptions |
| Route | Send the event and matching subscription IDs to each Gateway |
| Track progress | Track processed source position, including changes that produce no business event |

### 4.3 Capability Limits

- Source lookup and coalesced replay do not guarantee every historical transition.
- Tombstones are latest-state records, not retained before-images.
- Consumption progress does not by itself establish durable restart recovery or client acknowledgment.

The [Store Watch decision and integration limits](../../../../.agents/notes/implemented/architecture/2026-09-08-store-watch-contract.md) owns the implementation evidence and deferred capabilities.

## 5. Scalability & Partitioning

| Concern | Design option or constraint |
| --- | --- |
| Node state | Soft subscriptions restored by Gateways |
| Collection sharding | Assign different collections to different Streamers |
| Hash sharding | Route document-ID partitions to different Streamers |
| Gateway coverage | Connect to all responsible Streamers, or select them using the same partition rule |
