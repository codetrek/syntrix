# Streamer Overall Design

**Date:** January 3, 2026
**Status:** Design Draft
**Component:** Streamer

## 1. Service Interfaces (API)

Streamer consumes Puller subscriptions and serves Gateway subscriptions over a
bidirectional stream. Local and remote access share the same service contract.

### 1.1 Ingestion (Upstream Client)

| Boundary | Contract |
| --- | --- |
| Subscribe | Identify the consumer and provide its last processed opaque progress marker |
| Receive | Consume normalized MongoDB operations and their available document payloads |
| Convert | Produce business events before predicate matching |
| Resume | Reconnect from retained processed progress within the source's replay capability |

| Puller input | Business result |
| --- | --- |
| Insert carrying a live document | Create |
| Update/replace carrying a tombstone | Delete with retained reference/metadata, `deleted=true`, and `data={}` |
| Replace carrying a live document | Create, including recreation at a tombstoned path |
| Update carrying a live document | Update |
| Physical delete, including TTL cleanup | No matching or notification |

[Document Deletion and Physical Cleanup](../core/storage/03.stores.md#document-deletion-and-physical-cleanup) owns the lifecycle.

- Puller normalization and buffering retain source operation types.
- Business conversion suppresses physical cleanup; it must not become another logical delete.
- Lookup payloads and coalesced replay do not guarantee every historical transition. See the [capability limits](../../../../.agents/notes/implemented/architecture/2026-09-08-store-watch-contract.md).

### 1.2 Gateway API (Downstream)

One bidirectional gRPC stream carries control messages and event deliveries:

```text
Gateway -- Subscribe / Unsubscribe / Heartbeat --> Streamer
Gateway <-- EventDelivery / HeartbeatAck --------- Streamer
```

| Message | Fields |
| --- | --- |
| Gateway message | Exactly one of subscribe, unsubscribe, or heartbeat |
| Streamer message | Exactly one of event delivery or heartbeat acknowledgment |
| Subscribe request | Gateway-generated subscription ID, collection, repeated structured filters |
| Filter | Field, operator (`==`, `>`, `in`, etc.), value |
| Value | String, int64, double, boolean, or list of values |
| Event delivery | Business event and all matching subscription IDs for that Gateway |

The stream interface supports send, receive, and closing the send direction.
A remote client maps those operations to gRPC messages.

## 2. Core Data Structures

### 2.1 Subscription Index

| Index | Key | Stored values |
| --- | --- | --- |
| Exact matches | Collection, document ID | Subscribers |
| Expression matches | Collection | Subscribers with compiled CEL programs |
| Gateway ownership | Gateway ID | Subscription IDs for disconnect cleanup |

Each subscriber identifies a Gateway, a subscription, and its active delivery stream.

### 2.2 Business Event

| Field | Purpose |
| --- | --- |
| Collection and document ID | Matching and routing identity |
| Operation | Business create, update, or delete |
| Decoded document | Predicate evaluation, including tombstone metadata |
| Encoded payload | Forwarding to Gateways |

A delete carries a tombstone with cleared business data. Former field values
require a separate historical-image capability. Physical removal has no
business event payload.

## 3. Component Responsibilities

```text
Puller subscription
       |
       v
    Ingestion --> Business events --> Event coordinator --> Gateway streams
                                             |
                                             v
                                     Subscription index
                                      /             \
                              Exact lookup       CEL evaluation
```

| Component | Ownership |
| --- | --- |
| Service facade | Shared stream contract for local and remote access |
| Ingestion | Source subscription, decoding, business conversion, and suppression of physical cleanup |
| Event coordinator | Initialize ingestion/matching, request matches, and dispatch deliveries |
| Subscription manager | Thread-safe registration/removal, exact and CEL matching, aggregation of matches, disconnect cleanup |
| Gateway transport | Active streams, control messages, protocol conversion, and flow control |
| Remote client | Expose the shared stream contract over gRPC |

Slow-Gateway buffering and drop/disconnect behavior remain a flow-control decision.

## 4. Event Flow

```text
Registration:
Gateway -- subscribe(chat_id=1) --> Coordinator --> Subscription index

Business event:
Puller -- source insert --> Ingestion -- create --> Coordinator
                                                     |
                                                     +--> Matching --> Subscription IDs
                                                     |
                                                     +--> Gateway event delivery

Physical cleanup:
Puller -- source delete --> Ingestion --> No business event
```

Within each subscription, matching and delivery preserve the received order of
business events. Parallel execution must use a partition rule that preserves
that ordering.
