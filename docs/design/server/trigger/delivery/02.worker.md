# HTTP Delivery Worker

## Overview

The DeliveryWorker executes HTTP webhook requests for delivery tasks.

## Interface

```go
// DeliveryWorker processes delivery tasks by making HTTP requests.
type DeliveryWorker interface {
    ProcessTask(ctx context.Context, task *types.DeliveryTask) error
}
```

## Request Building

### URL

From `task.URL`:

```go
req, err := http.NewRequestWithContext(ctx, "POST", task.URL, body)
```

### Headers

1. **Content-Type**: Always `application/json`
2. **Custom Headers**: From `task.Headers` map
3. **Signature**: HMAC-SHA256 signature (if secret configured)
4. **Authorization**: Bearer token (if auth configured)

```go
// Base headers
req.Header.Set("Content-Type", "application/json")

// Custom headers
for k, v := range task.Headers {
    req.Header.Set(k, v)
}

// Signature
if secret != "" {
    sig := hmacSHA256(body, secret)
    req.Header.Set("X-Syntrix-Signature", sig)
}

// System token
if token != "" {
    req.Header.Set("Authorization", "Bearer " + token)
}
```

### Body

JSON-encoded payload:

```json
{
    "trigger_id": "notify-on-order",
    "database": "myapp",
    "event": "create",
    "collection": "orders",
    "document_id": "order123",
    "payload": {
        "id": "order123",
        "status": "pending",
        "amount": 100
    }
}
```

## Authentication

### Secret Resolution

Secrets are resolved via `SecretsRef`:

```go
if task.SecretsRef != "" {
    secret, err := w.secretProvider.GetSecret(ctx, task.SecretsRef)
    if err != nil {
        return err  // Fail task, retry later
    }
    // Use secret for signing
}
```

**Important**: Secrets are database-scoped. Cross-database reuse is forbidden.

### HMAC Signature

```go
func hmacSHA256(body []byte, secret string) string {
    h := hmac.New(sha256.New, []byte(secret))
    h.Write(body)
    return hex.EncodeToString(h.Sum(nil))
}
```

The signature is set in the `X-Syntrix-Signature` header.

### System Token

For internal services, a system token can be minted:

```go
if w.auth != nil {
    token, err := w.auth.MintToken(ctx, task.Database)
    if err != nil {
        return err
    }
    req.Header.Set("Authorization", "Bearer " + token)
}
```

## Response Handling

HTTP 2xx returns success. HTTP 400–499 responses other than 429 return a
`FatalError`; 429 and all other non-2xx responses returned by the HTTP client
return ordinary errors containing the response status. The same fatal predicate
sets the failure metric's fatal flag, so metrics and consumer behavior agree.
Transport errors and attempt timeouts remain retryable and preserve their error
chains.

HTTP 429 is retryable because an endpoint's throttling can recover after a delay.
The consumer applies its existing attempt budget and rule backoff. See the
[classification decision](../../../../../.agents/notes/implemented/bug-fix/2026-09-07-trigger-retryable-http-statuses.md)
for the alternatives and accepted costs. Redirect handling remains the HTTP
client's responsibility; this classification applies to responses it returns.

## Timeout

Tasks have a configurable timeout:

```go
timeout := time.Duration(task.Timeout)
if timeout == 0 {
    timeout = types.DefaultTaskTimeout  // 30s
}

ctx, cancel := context.WithTimeout(ctx, timeout)
defer cancel()
```

## Retry Policy

The worker performs one HTTP attempt. The
[consumer](01.consumer.md#retry-behavior) owns total attempt accounting and
queue-delayed retries using the task's `maxAttempts`, `initialBackoff`, and
`maxBackoff`. The [public guide](../../../../reference/trigger_rules.md#delivery-retries)
defines those fields and terminal behavior.

`Retry-After` response hints are not used. Their parsing and interaction with
rule backoff remain in the independent
[Retry-After proposal](../../../../../.agents/notes/proposed/feature/2026-09-07-trigger-retry-after.md).

## Error Types

A `FatalError` terminates delivery immediately. Other non-nil errors enter the
consumer's retry policy. HTTP failures retain the status in the error message;
wrapped transport errors retain their underlying cause. The worker uses this
existing distinction for 429 without adding a new retryable error type.

## Observability

### Metrics

| Metric | Tags | Description |
|--------|------|-------------|
| `trigger.worker.request.count` | database, status_code, success | HTTP requests |
| `trigger.worker.request.latency` | database | Request latency |
| `trigger.worker.retry.count` | database | Retry attempts |

### Logging

| Event | Level | Description |
|-------|-------|-------------|
| Request started | Debug | HTTP request initiated |
| Request success | Debug | 2xx response |
| Request failed (retry) | Warn | 429, other nonterminal HTTP failure, network error, or attempt timeout |
| Request failed (fatal) | Error | 4xx (non-429) |
| Secret fetch failed | Error | SecretsRef resolution error |
