# Trigger Evaluator Checkpoints

The evaluator saves one opaque aggregate Puller progress marker at
`sys/checkpoints/trigger_evaluator`, in the configured checkpoint database
(default `default`). The consumer label is `trigger-evaluator`.

## Why one checkpoint

A Puller progress marker contains independent source/generation/sequence positions
across all configured physical sources. A logical Syntrix database is event
metadata and can share a MongoDB source with other logical databases. Splitting
that marker into per-database checkpoints could overwrite unrelated progress.

```text
Puller Subscription.Next()
          |
          v
Watcher: transform or progress-only envelope
          |
          v
Evaluator: select matching database/rules and publish tasks
          |
          v
Completed aggregate progress -> asynchronous checkpoint writer
```

The marker is not a MongoDB resume token. The watcher preserves it unchanged;
Puller owns validation, replay, source identity, and history boundaries.

## Startup

`DocumentWatcher.Watch` returns a `WatcherStream` with `Next(ctx)` and `Close()`.
It loads the checkpoint before calling the shared Puller subscription API.

| Stored state | Result |
|---|---|
| Valid nonempty token | Subscribe with that marker |
| Missing record and `StartFromNow=true` | Subscribe from current published heads |
| Missing record and `StartFromNow=false` | Return the missing-checkpoint error |
| Unreadable record, empty token, or wrong token type | Return an error |
| Cursor generation/source/history mismatch | Preserve Puller's typed failure |

`StartFromNow` is an explicit bootstrap decision, not recovery from malformed or
expired history. The first subscription envelope reports the effective initial
progress and is checkpoint-eligible without a document.

## Processing and persistence

The watcher transforms document events and preserves progress-only messages.
Physical MongoDB deletes represent storage cleanup and become progress-only
messages; an invalid transformation terminates the stream. Logical database
selection happens during rule evaluation, not by discarding pieces of the
aggregate marker.

The evaluator processes events sequentially. Evaluation or task-publication
failure returns an error before making that event's progress checkpoint-eligible.
Only a fully processed prefix reaches the asynchronous checkpoint writer. It
coalesces completed markers and stops consumption if saving fails.

The stored document data is:

```json
{
  "token": "opaque-puller-progress",
  "updatedAt": 1788739200
}
```

`updatedAt` uses Unix seconds. Save updates the existing checkpoint and creates
it only when storage reports not found. Other errors remain visible.

When the source ends, the evaluator cancels its owned saver context before
joining the saver and closing the stream. Cancellation may leave completed work
unsaved; replay can repeat it. Shutdown does not claim that every completed event
has been durably checkpointed.

## Remaining scheduling guarantee

The current completion point is successful evaluation and publication through
the configured publisher. There is no durable scheduling outbox that atomically
retains rule selection and every matched task. Standalone memory publication
also does not become durable merely because Puller is durable.

[Durable scheduling](../../../../../.agents/notes/proposed/architecture/2026-09-07-trigger-delivery-idempotency.md)
and [checkpoint advancement after scheduling](../../../../../.agents/notes/proposed/bug-fix/2026-09-07-trigger-publish-checkpoint-ordering.md)
own that stronger guarantee. A crash after partial fan-out can repeat tasks and
can reevaluate against a changed rule set. A history gap requires an operator
incident/reconciliation decision; a current document snapshot cannot recreate
historical Webhook effects.

Only one evaluator should own a shared checkpoint until ownership transfer or
leader coordination is implemented. Multiple writers can overwrite progress and
duplicate processing.
