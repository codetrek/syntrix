# CEL Evaluator

The evaluator applies CEL conditions to Syntrix business events. Separating
event matching from payload availability lets a deletion rule match retained
identity without implying access to deleted business data.

## Evaluation Boundary

```text
Business event + trigger definition
                |
                v
Database / event type / collection pattern
                |
                +---- mismatch ----------> No match
                |
                v
          CEL condition
                |
                +---- true / empty ------> Match
                +---- false -------------> No match
                +---- invalid / error ---> Evaluation failure
```

Conditions must return a boolean. Reuse compiled conditions to avoid repeated
compilation.

## Supported Event Context

The single CEL variable is `event`. Business fields are flattened into the
document map; metadata wins when field names collide.

| Field | Meaning | Current availability |
|---|---|---|
| `event.type` | `create`, `update`, or logical `delete` | Every business event |
| `event.timestamp` | Puller normalization time, Unix milliseconds | Every business event |
| `event.document` | Current business data plus stored `id`, `collection`, and `version` | Logical deletion retains only these metadata fields |
| `event.before` | Previous document image | `null` on the current production input path |

- `event.document.id` is the storage identifier; original business-ID access is
  not guaranteed.
- The CEL context has no raw update description or storage `deleted` flag.
- Document deletion is identified with `event.type == "delete"`.

## Document Deletion and Before Images

```text
Logical delete
    |
    v
Tombstone: deleted=true, data={}, retained metadata
    |
    +----> Business delete ----> CEL document: id / collection / version
    |
    v
Later physical cleanup ------> No business trigger event
```

This follows the [storage deletion lifecycle](../../core/storage/03.stores.md#document-deletion-and-physical-cleanup).
An update or replacement carrying a tombstone produces the business deletion;
physical document removal is excluded.

| Capability | Supported now | Proposed historical-image capability |
|---|---|---|
| Match logical deletion | Event type and retained metadata | Unchanged |
| Read previous business fields | Unavailable for create, update, and delete input | Genuine previous image for requested updates and logical deletes; no previous image for creates |
| `includeBefore` | Does not enable capture | Controls exposure of a captured image to the rule |
| Required image unavailable | No historical-image guarantee | Explicit activation failure, or event failure with a recoverable position |

[Capture Trigger Before Images](../../../../../.agents/notes/proposed/feature/2026-09-07-trigger-before-images.md)
owns source prerequisites, retention, transport, and exposure. An optional field
alone cannot provide historical data.

## Matching and Failure Behavior

| Condition or input | Evaluation result | Rule-author consequence |
|---|---|---|
| Database, event type, or collection mismatch | No match | No task |
| Empty condition after scope matches | Match | No field condition is required |
| Boolean CEL expression | Match or no match | Only `true` creates a task |
| Invalid CEL, non-boolean result, missing-field access, or null-image dereference | Evaluation failure | Guard optional fields with `has(...)` and optional images with a null check |
| Condition needs a previous business value | Unsupported on current production input | A guard prevents an access error but cannot recover historical data |

Current service handling logs evaluation failures and skips that rule for the
event. This is an implementation limitation, not a recovery guarantee.
[Rule evaluation controls](../../../../../.agents/notes/proposed/bug-fix/2026-09-07-trigger-rule-filter-evaluation.md)
track validation and failure handling; [before-image capture](../../../../../.agents/notes/proposed/feature/2026-09-07-trigger-before-images.md)
tracks required-image failures.

## Rule Examples

| Intent | CEL condition |
|---|---|
| Premium document created | `event.type == "create" && event.document.type == "premium"` |
| Updated document is shipped | `event.type == "update" && event.document.status == "shipped"` |
| Account logically deleted | `event.type == "delete" && event.document.collection == "accounts"` |
| Approved, high-value update | `event.type == "update" && event.document.status == "approved" && event.document.amount > 1000` |

An updated-state condition does not establish that the field changed. Comparing
old and new values requires the proposed historical-image capability.

Collection patterns use glob matching; `*` matches within one path segment.

| Collection pattern | Selection |
|---|---|
| `users/profiles` | Exact collection |
| `orders/*` | One collection segment below `orders` |
| `tenants/*/users` | Each tenant's `users` collection |

See the [Trigger Rules Guide](../../../../reference/trigger_rules.md) for complete
configuration examples.
